# context-keeper 规范

`organize-context` 和 `record-context` 共用这份规范。目标：**常驻 context 尽量小，其余按需加载。** 读代码得不到的知识放在离用到它的代码最近、又不会被无关任务读到的地方：

- 只和一个文件（或其中一段代码）有关的，写成**代码注释**，紧贴相关代码，简短；
- 几个文件共用的，写成带 `paths` 的 **rule**；
- 任何任务都可能违反的硬约束，才进 **CLAUDE.md**；
- 以上三处需要的**扩展内容**（决策的原因、怕有人重提的放弃方案、实测数据、外部系统调研），以及挂不到代码上的背景，过了「准入门槛」的进**项目文档**（`context-docs/`）。原处只留「一句话重点 + 什么时候读 + 路径」的指针，由 Claude 按需读。

## 加载机制（2026-09 已核实，直接按此执行；实际观察与某条矛盾时以观察为准，并在计划或报告里指出）

1. `.claude/rules/` 下的 `.md`（递归发现，可用子目录组织）带 `paths:` glob → 只有读/改到匹配文件时才进 context。没有 `paths` 的 rule 常驻，`paths` 只有 `"**"` 的也常驻。`paths` 可以是列表或逗号分隔的字符串，支持花括号（`*.{ts,tsx}`），按 **gitignore 语义**匹配：不含 `/` 的模式（`*.test.ts`）匹配任意深度；含 `/` 的相对作用域根锚定；匹配到目录就等于匹配目录下所有文件，所以 `src/api`、`src/api/**` 等价，`src/*` 等于整个 `src/`；`./` 开头的匹配不到任何文件（2026-11 读 Claude Code 2.1.319 源码核实）。
2. 子目录里的 `CLAUDE.md` → 碰到那个目录的文件时才加载，但**一旦触发是整文件加载**，也不支持 `paths:`。
3. Skill → 启动时只加载 description。子包的 `.claude/skills/` 也有效，碰到该包的文件后才可用，重名时用 `apps/web:deploy` 这种目录限定名。
4. 子包的 `.claude/rules/` 同样有效，**`paths` 相对该子包解析**（官方文档没写，已实测）。
5. **`@path` import 是 eager 的**，启动就展开进 context，完全不省 token。**禁止**用它来"拆分"。
6. 自动记忆在 `~/.claude/projects/<project>/memory/`，不在仓库里，只对当前用户、当前机器生效；`MEMORY.md` 前 200 行常驻。

由此得出几点：

- **根 CLAUDE.md 和目录级 CLAUDE.md 都要瘦**。根的常驻；目录级的触发即全量——一个 400 行的包级 CLAUDE.md，碰了包里任意一个文件就全进来。
- **只匹配一个文件的 rule，和写在那个文件里的注释成本一样**：碰到文件就整条加载，Claude 只读文件的一部分时也一样。它比注释差在离代码远、定位不到函数，所以单个文件的内容写成注释；rule 留给几个文件共用的内容，以及没法写注释的文件（见「标签与去处」）。
- **写在原处的内容一定被看到，项目文档要 Claude 自己决定去读。** 所以必须知道的那一句（坑、约束）留在原处，只有扩展内容进文档；指针要写清"什么时候读"，Claude 才判断得准（见「指针」）。改代码时还有 `pointer-guard` hook 兜底（见「hook」）。进了 `context-docs/` 的文档必须至少被一处指到，光写进去等于没写（见「项目文档」）。

## 仓库形态与作用域

### 判断形态

命中下列任一信号即为 **monorepo**，否则为**单仓库**：

- `pnpm-workspace.yaml`、根 `package.json` 的 `workspaces`、`lerna.json`、`nx.json`、`turbo.json`、`rush.json`
- `Cargo.toml` 的 `[workspace]`、`go.work`、`settings.gradle(.kts)` 的 `include`、`pom.xml` 的 `<modules>`
- 以上都没有，但有多个带独立清单文件且各自构建的目录——拿不准，说明依据，让用户确认

**包**是 workspace 配置实际匹配到的成员目录，以配置为准，不凭目录名猜。

### 作用域

**作用域**是一套 `CLAUDE.md` + `.claude/` + `context-docs/` 的挂载点：单仓库只有仓库根一个；monorepo 是仓库根加每个包。包的 `.claude/`、`context-docs/` 只在真有内容时才建。

- 内容涉及的文件全在某个包内 → 该包；涉及两个及以上包 → 根；单仓库 → 一律根。
- `.claude/` 只放 Claude Code 要从这里加载的东西。本规范往里写的只有 `rules/`、`skills/`；已有的 `settings*.json`、`commands/`、`agents/`、hook 脚本等原样保留。
- 根 CLAUDE.md 可以是 `CLAUDE.md` 或 `.claude/CLAUDE.md`，两者等价；两个都存在时交给用户决定是否合并。
- 项目文档放 `context-docs/`。**不放 `.claude/`**：Claude 偶尔会把 `.claude/` 下的文件当成敏感配置而拒绝编辑。**不用点开头的 `.context/`**（0.7.x 及更早用的）：rg 和 Grep 默认跳过隐藏目录，搜不到里面的文档。**不用 `context/`、`_context/`**：前者常被项目代码占用，后者是 Next.js 等框架私有目录的写法（`app/_context/`），也常放代码；带连字符的 `context-docs` 基本不会是代码目录。
- `.claude/` 是点开头的目录，有些工具默认跳过它：Grep / Glob 时显式传 `.claude/` 作为 path。`context-docs/` 必须进 git：被 `.gitignore` 忽略、或已被别的用途占用（有被代码或工具读取的文件）时不往里写，交给用户决定。
- `.claude/rules/`、`.claude/skills/` 同样必须进 git。不少项目把 `.claude/` 整个忽略，或只放行 `settings.json`：这时写进去的 rule、skill 只在本机生效，队友看不到。新建前用 `git check-ignore` 确认，被忽略就交给用户调整 `.gitignore`（通常只需要忽略 `settings.local.json`）。

### 目录级 CLAUDE.md

单仓库的子目录（如 `src/server/CLAUDE.md`）或包内更深层的 CLAUDE.md，按包级同样的标准瘦身：只留"该目录内任何任务都适用"的。**不要**在这些目录下另建 `.claude/` 或 `context-docs/`，拆出来的东西放进所属作用域。**不要**为了放某条规则新建目录级 CLAUDE.md，没有的走 rule。

## 准入门槛

写进仓库的每一行都有成本：常驻的占 context，按需的要维护指针，过时了会误导。所以先问「值不值得留」，再问「放在哪」。**拿不准时不记**：漏记一条，代价是某次多读几分钟代码；多记一条，以后每次改动都要维护它。git 历史和 PR 描述一直都在，删掉的内容随时找得回来。

一条内容同时满足下面三条才准入：

1. **有具体的错**：写得出一句「不知道这条，Claude 会做 X，结果是 Y」。写不出具体动作的（「了解背景有帮助」「以后可能用得上」）不准入。
2. **拦不住**：这个错不会被类型检查、测试、lint、CI、构建失败、运行时报错拦下，读那几行代码也看不出来。拦得住的不记；本该拦住却没拦住的，标 `HOOK`。
3. **静默或代价高**：错了不报错（数据静默丢失、页面静默不显示、口径静默混算），或者代价高、难回滚（线上事故、账单、数据损坏、对外发布）。会立刻报错、一分钟就能改回来的，不记。

**扩展内容单独过门槛**，不因为它的重点准入了就跟着进来。扩展内容（文档，以及注释第二句以后的部分）还要答得出：「什么任务会让 Claude 去读它，读完会改变哪个决定？」答不出就不留。下面这些默认不准入：

- 时间线、排障流水、「某天发现 → 某天改 → 某天又改回」的经过：结论写在原处，经过留给 commit 和 PR
- 已被推翻的方案的完整论证：只有怕有人重提时，才留一两句「试过 X，因为 Y 放弃」，并进现行方案的文档，不单独成文件
- 推导过程：留结论和会让结论失效的条件，推导删掉
- 只是把一句注释换个地方存的文档：原处已经写了重点、文档里没有多出新事实的
- 原文就没有日期和测法、也没有任何决策依赖它的数字

例外：评估需求时要用到的外部约束和预算（体积上限、配额、计费档位）及其实测数字，只要满足第 1、3 条就准入，不要求第 2 条。

几个例子：

- 准入：「新增错误类型时，`apps/web` 必须先上线认识它，生产方才能开始写」。顺序反了，统计会静默算错，类型和测试都拦不住，三条都满足。
- 准入：「pnpm 给脚本传参不要写 `--`」。后面的参数会被静默吃掉，然后跑一遍全量任务。不报错、代价高。
- 准入（例外）：「Worker 上限 10 MB（gzip 后）」。超了部署会报错，第 2 条不满足；但等到部署失败才发现，功能可能已经白做了，评估要不要引入一个依赖时就得知道，按例外准入。
- 不准入：支付回调超时取 5 秒，注释里已经写了「上游最慢 3 秒，留余量」，拆出来的文档里「背景」「放弃的方案」两节都是 `未记录`，「决定」一节和注释说的是一回事。删掉文档和指针，注释原样保留。
- 不准入：网关切换的排障记录，「周一发现 → 周二改 → 当天又改回」。结论（现在用哪个、为什么）写在原处，经过留给 commit。

## 标签与去处

| 标签 | 判据 | 去处 |
|---|---|---|
| `ALWAYS` | 任何任务都可能违反的硬约束（commit 规则、语言/风格约定、绝对禁止做的事） | 全仓通用 → 根 `CLAUDE.md`；只在某包 / 某个已有目录级 CLAUDE.md 所在目录内成立、且其中任何任务都适用 → 那个 CLAUDE.md。一条一行，有扩展内容时同一行末尾加指针 |
| `HOOK` | 能被脚本/lint/CI 确定性校验、但现在还没被拦住的（「准入门槛」第 2 条就是这个标签的来源） | 建议改成 hook 或 lint。**只提建议，不自己改 CI**。检查落地前文字不删，继续按阶梯归类放好；落地后由用户删，或 organize-context 体检时列出来 |
| `COMMENT` | 只和**一个文件**（或其中一个函数、一段代码）有关、且这个文件能写注释的："做什么"（"这个值不能超过 3"、"顺序不能换"）、坑、一句原因 | 代码注释，紧贴相关代码：函数 / 常量上方，涉及整个文件的写在文件头。1–3 行。过了门槛的扩展内容拆成 `DOC`，注释里留指针 |
| `PATH-RULE` | 只在碰到特定文件时才需要知道、但**涉及多个文件**的：一类文件的约定、一个目录的坑、"改 A 必须同步 B"；以及只涉及一个文件、但这个文件**没法写注释**的（JSON、lockfile、生成物、二进制资源，或写了会被工具覆盖） | `<作用域>/.claude/rules/<领域>/<name>.md`。"做什么"加一两句原因，正文不超过 10 行。过了门槛的扩展内容拆成 `DOC`，rule 里留指针 |
| `SKILL` | 有步骤的流程（发布、迁移、排障 playbook），平时不需要 | `<作用域>/.claude/skills/<name>/SKILL.md` |
| `DOC` | 读代码得不到、原处又不该展开、且通过「准入门槛」的：一是**扩展内容**，即注释、rule、CLAUDE.md 里那一句话之外的部分（决策的原因、怕有人重提的放弃方案、实测数字和它的历史、外部系统调研）；二是**挂不到具体代码上**的（评估过但没做的需求、外部系统的限制、还没有对应代码的决定、领域知识） | `<作用域>/context-docs/<领域>/<slug>.md`。第一种由原处的指针登记（注释、rule 或 CLAUDE.md 里那一行），领域里多处都该知道、又不属于某一处的登记进领域索引 rule；第二种登记进 `<作用域>/context-docs/README.md`（见「项目文档」） |
| `DERIVABLE` | 没过「准入门槛」的：读代码就能知道的、只是复述某次需求做了什么的（commit 的职责），以及经过、流水、推导、没人用的数字 | **删除** |
| `STALE` | 已不成立、与现状矛盾、或引用了不存在的文件 | **删除**，单独列出让用户确认 |
| `PERSONAL` | 个人偏好、对 Claude 的纠正、个人工作习惯 | 不进仓库，留在自动记忆。想对所有项目生效时，给出可粘贴到 `~/.claude/CLAUDE.md` 的文本，**不直接改那个文件** |
| `ENV-BOUND` | 换台电脑、网络、操作系统就不成立的：本机路径、本机版本、端口占用、代理/网络、只在某台机器出现的怪现象、凭据 | 不进仓库，留在自动记忆 |

有条件成立的（"在 macOS 上 X 会失败"、"Node 20 以下会报 Y"）不算 `ENV-BOUND`：换台同类环境照样遇到。按上表正常归类，**正文第一行写明适用条件**（如"仅 macOS："）。

**敏感信息一律不进仓库**，不论原本是什么标签：API key / token / 密码 / 私有仓库地址 / 内网 IP 或域名 / 含用户名的绝对路径 / 任何用户没打算公开的信息。向用户报告时只说类型和位置，不打出值本身。

## 判据阶梯

按顺序问，第一个"是"就停。一条内容混着"做什么"和"为什么 / 经过 / 数字"时，先拆成两部分：**必须知道的那一句**（做什么、坑，加一句原因）按阶梯定去处；**扩展内容**（第二句以后的原因、经过、数字）单独过「准入门槛」，过了才是 `DOC`，原处留指针（见「扩展内容与指针」），过不了的删掉。整条两三行就说完的不拆，原样写在去处。

0. 它属于这个项目吗？个人偏好 → `PERSONAL`；换台机器就不成立 → `ENV-BOUND`
1. 过「准入门槛」了吗？没过 → `DERIVABLE`，删除。只有重点过了、扩展内容没过的，重点照常往下走，扩展内容直接删，不拆成 `DOC`。commit 里写过不等于不用记：过了门槛的照样写进仓库（Claude 平时不翻 git 历史）；没过的，commit 里写过也不记
2. 能写成脚本自动校验吗？能 → 同时打上 `HOOK`，但**不停**，继续往下问，定出检查落地前文字放哪
3. 有步骤、平时用不上吗？是 → `SKILL`
4. 只在碰到特定文件、目录或文件类型时才需要知道吗？是 →
   - 适用于某个已有目录级 CLAUDE.md 所在目录内任何任务 → `ALWAYS`，放进那个 CLAUDE.md
   - 适用于某个包内任何任务（monorepo）→ `ALWAYS`，放进那个包的 CLAUDE.md（没有就新建），不写成覆盖整个包的宽 rule
   - 只涉及一个文件、且这个文件能写注释 → `COMMENT`，写在相关的函数、常量上方；涉及整个文件的写在文件头
   - 否则（涉及多个文件，或文件没法写注释）→ `PATH-RULE`

   "涉及几个文件"按**谁需要知道**算，不按这条知识讲的是哪个文件算。约束的是调用方的（"必须在 X 之后调用""返回值不能缓存"），需要知道的是调用它的那些文件，写在定义上方的普通注释里，写调用代码时不一定读得到：调用方分散的，写进定义处的 API 文档注释（JSDoc / docstring，属于"怎么用"，查定义、IDE 悬停时看得到，不受 1–3 行限制）；调用方集中在某个目录的，写成 `paths` 覆盖调用方的 `PATH-RULE`。

   这一步要严格：能挂到代码上的都挂上，能挂到一个文件上的不写成 rule。
5. 是背景（原因、数字、外部约束、评估过但没做的需求），但挂不到具体代码上吗？是 → `DOC`，登记进 `context-docs/README.md`
6. 剩下的"做什么"才是 `ALWAYS`

## 扩展内容与指针

### 什么时候拆

先删后拆：超出原处的部分先过「准入门槛」，过了的才拆进文档。过不了的直接删，不为了保留它去建文档。

注释、rule、CLAUDE.md 里只放**必须知道的那一句**：做什么、坑，加一句原因。超出的部分过了门槛的拆进文档，原处留指针：

- 注释超过 3 行，或要讲试过的方案、数字
- rule 正文（不算 frontmatter 和空行）会超过 10 行
- 实测数字和它的历史：会一直追加。原处可以写当前值
- 同一段背景要被几处共用（几条 rule、几个文件的注释）：一件事只写一处

两三行就说完的不拆，直接写在原处。为了格式统一硬拆成"一句话 + 指针"，只会多一次读文件。

### 指针怎么写

指针是原处的一行：**重点 + 什么时候读 + 仓库根起的路径**，可以在括号里写文档里有什么。

```ts
// 重试上限 3：网关连续 5 次失败会封 IP 10 分钟，按出口 IP 算。改重试次数、并发或超时前读 apps/web/context-docs/api/upstream-gateway.md（封禁的计算口径、各接口实测延迟）
```

- **重点**：文档里不知道就会做错的结论（坑、约束、已知限制）必须写，写成照着做就不会出错的话。这样 Claude 没去读文档也不会踩坑，漏掉的只是细节。反过来，只有路径和触发条件的指针，Claude 得读完整份文档才拿得到重点，重点和细节还是一起进了 context，等于没拆。文档里没有这类结论的（纯历史、纯数据，没有"此处别乱动"的意思）才可以省掉。
- **什么时候读**：写成动作（"改 X 前""要调 Y 时""评估 Z 前"），不写成话题（"X 的背景见""原因见"）。Claude 能拿动作和当前任务对照，话题只能靠猜。
- **路径**：纯文本路径（注释里的、反引号包住的、裸写的）从仓库根起写，指向整份文档；要定位到某一节时在括号里写节名，不用 `#锚点`。
- **Markdown 链接**：链接目标按 Markdown 的规矩写**所在文件起的相对路径**（`apps/monitor/context-docs/models/a.md` 里写 `[迁移记录](../targets/b.md)`），GitHub 和 IDE 预览按所在文件的目录解析，写成仓库根起的路径点开就是 404。开头是 `/` 的（`/apps/monitor/context-docs/targets/b.md`）按仓库根解析，也行。链接文字随意（标题、文件名都行）；链接文字里也写了路径的，按纯文本路径算，从仓库根起写，和链接目标指向同一份文档。源码注释里不用链接语法。已经有效的相对链接不要改写成仓库根起的路径。
- **放在离代码最近的地方**：函数 / 常量上方的注释 > 文件头注释 > rule > CLAUDE.md。越近，触发条件越具体，误读、漏读都越少；`pointer-guard` hook 也只认注释里的指针。
- 一份文档可以被几处指到，每处按自己的位置写重点和触发条件。指针只是登记，不算"一件事写两处"。
- 不留 `// 见文档`、`原因见 X` 这种没有重点、也没有触发条件的指针。
- 领域索引 rule、`context-docs/README.md` 里的登记行也是指针，按同样的格式写（见「入口」）。

## 项目文档

### 位置与命名

- 路径：`<作用域>/context-docs/<领域>/<slug>.md`。涉及两个及以上领域、或说不清属于哪块的，放 `context-docs/` 顶层。
- **领域**指"讲的是系统哪一块"（`api`、`db`、`styling`），取自项目已有叫法：优先用同作用域 `.claude/rules/<领域>/` 已在用的名字，其次用代码里的模块名、目录名，不自造。rules 和 `context-docs/` 共用同一套领域名。**第一份文档就放进领域目录**，只分一层，不嵌套。
- **不按信息类型分目录**（不建 `decisions/`、`data/`、`pitfalls/`）：要改支付模块时，想看的是支付相关的一切，不管它是原因、数字还是坑。
- `context-docs/README.md`（只认作用域 `context-docs/` 顶层这一个）是文档入口，不是文档，见「入口」。
- 文件名 `<slug>.md`：英文小写短横线，概括主题（`retry-policy`，不是 `fix-bug`）。**不带日期、不带编号**：文档描述现状、原地更新，创建日期没有意义；两个分支为同一主题各建一份时，同名文件会在合并时冲突，正好把重复暴露出来。

### 入口

文档不会自动加载，每份都要被至少一处指到，否则基本不会被读到。按文档是从哪里拆出来的、能不能挂到代码上选：

| 文档 | 入口 | 什么时候被看到 |
|---|---|---|
| 从某处拆出来的扩展内容 | 原处的指针：代码注释、rule 或 CLAUDE.md 里那一行 | 读到那段代码 / 碰到那条 rule 的 `paths` / 一直 |
| 能挂到代码上、但不属于某一处的（外部系统调研、领域内几处共用的数据） | 领域索引 rule `<作用域>/.claude/rules/<领域>/context-index.md` | 碰到这个领域的代码时 |
| 挂不到代码上（评估过但没做的需求、外部系统限制、还没有代码的决定） | 文档入口 `<作用域>/context-docs/README.md`，由根 CLAUDE.md 常驻一行指过去 | 做新需求、评估方案前 |
| 两个时候都要看到的（见下文「两边都登记」） | 代码那一侧的入口（指针或领域索引）和 `context-docs/README.md` 都登记 | 两者 |

领域索引 rule 和文档入口的正文都是每份文档一行，按「指针怎么写」写：**重点 + 什么时候读 + 仓库根起的路径**（模板见 templates.md）。只列路径和"什么时候读"的登记行没有用：入口进了 context，Claude 什么都没得到，要读完整份文档才知道重点。判断办法：不读文档、只看这一行，会不会做错？会，就把不做错所需的结论写进这一行；文档里没有这类结论的（纯参考）才省掉重点。入口里只写结论，经过、实测数字、表格留在文档里，不抄进来（约束本身的阈值（"每秒 50 次""上限 50MB"）是结论的一部分，写在登记行里）；会变的当前值（已用多少、当前体积）也留在文档里：写进登记行，文档每改一次都得跟着改，漏改了脚本查不出来。

**从某处拆出来的文档**：原处的指针已经保证碰到相关代码时能看到，不用再进领域索引；只有希望碰到整个领域的代码时都看到，才另外登记进索引。

**领域索引 rule**：每个有不属于某一处的文档的领域一个，`paths` 覆盖这个领域的代码。碰到该领域的代码时，每份文档的重点随 rule 自动进 context，成本只有几行；细节仍按需读。一份文档的重点一句话写不完（有好几条结论）的，不进索引，单独写成一条 rule：`paths` 覆盖相关代码，正文是这几条结论加指针。顶层的跨领域文档，登记进每个相关领域的索引。

**文档入口**：每个有这类文档的作用域一个 `context-docs/README.md`。它是挂不上 `paths` 的知识唯一的触发点，所以根 CLAUDE.md 的「更多上下文」里必须有一行，写明所有作用域的 `context-docs/README.md` 路径（包级 CLAUDE.md 碰到包里的文件才加载，等不到"提需求"的时候）。入口里的文档挂不到代码上，重点一句话写不完时没有 rule 可拆，也不从入口里拿掉：登记行写评估需求时最容易做错的那一条，括号里点出文档里还有哪几条结论。

**两边都登记**：一份文档在"改代码时"和"评估新需求时"都要被看到，就同时登记进代码那一侧（原处的指针或领域索引 rule）和 `context-docs/README.md`，两行各写各的重点和"什么时候该读"。登记行只是指针，不算"一件事写两处"。典型的有：

- 挂得到代码上、但评估需求时也要考虑的：安装包体积、性能预算、外部系统的配额和限流——"做这个功能会不会超"在动代码之前就要知道
- 挂不到代码上、但和某个领域的代码也有关系的：某模块评估过但没做的功能，改那个模块时也值得看一眼

只在改代码时才用得上的文档不进 `context-docs/README.md`：它是每次做新需求都要过一遍的清单，越短越好。

新建、改名、删除文档时同步改入口。文档里的结论变了，登记行的重点也在同一次改动里改掉（grep 文档路径找出所有登记它的行，两边都登记的有两行）：Claude 看了重点多半不会再去读文档，过时的重点比没有重点更糟。Claude 改文档时 `doc-hook` 会列出指到它的行提醒一次；人手改的文档、提醒了没改的，要等 organize-context 体检时逐行对着文档看才查得出来。

### 内容

- **按主题组织，不按需求组织。**"这次做了什么"由 commit 记录，不要每做一个需求就落一个文档。一个主题一份，优先改已有的同主题文档。
- 第一行是标题，说清讲的是什么。没有固定模板，怎么分节按内容定。
- **写的是现状。** 情况变了就原地改写，不追加"更新：……"，不另建新文件再把旧的标成作废。改代码让指针里的重点（比如当前值）或文档里的说法不再成立时，在同一次改动里把指针、登记行里的重点和文档都改掉，不等下次体检。旧说法交给 git；以后还用得上的历史留在正文里：
  - 被放弃的方案只在"怕以后有人重新提"时才留，一两句话写明放弃了什么、为什么。
  - 评估过但没做的需求：写明卡在哪（哪个外部系统、什么限制）、评估的时间，以及什么条件变了值得重新评估。
  - **实测数字**：只留过了「准入门槛」的（有决策依赖它，或是评估需求要用的外部约束、预算）。每个都带测出它的日期和测法；迁移来的原文没写就标 `未记录`，不编造。过不了门槛的整节删掉，不为了凑结构写 `未记录`：一份文档的各节大半只能写 `未记录`，说明它不该存在。同一指标测出新值时追加一行（表格见模板），不覆盖旧值；被测的东西已经没了才删。
- 文档只写背景。能挂到代码上的"做什么"写在原处（注释或 rule），原处留指针指向文档。

### 移动、改名、删除

会让指向它的入口（领域索引 rule、`context-docs/README.md`）、rule、代码注释里的指针、CLAUDE.md 失效。先在**整个仓库** grep 旧路径找出所有指针，一并改掉；整份删掉的把指针行一起删。Markdown 链接写的是相对路径，按旧路径 grep 不到，再按文件名 grep 一遍；移到别的目录时，这份文档自己往外指的相对链接也要跟着改（移动前后各跑一次检查脚本，失效的链接会报出来）。有指针落在本次不可写的文件里，就不动这份文档，只提建议。移动和改名只在 organize-context 里做，record-context 不挪已有文件。

## 硬约束

- **禁止 `@` import**，指路一律用自然语言写**仓库根起的路径**（方便 grep 和脚本校验）；Markdown 链接的目标例外，写所在文件起的相对路径（见「指针怎么写」）。
- **`paths` 要窄到能真正起过滤作用。** 不许写 `**/*`、`src/**`、`src/*`、`packages/**` 这种一碰作用域就全中的；领域级的 `src/api/**` 可以。glob 相对 rule 所属作用域的根写（包内 rule 相对包目录，根 rule 从仓库根写完整路径），必须至少匹配到一个现存文件。例外：指向生成物或被 `.gitignore` 忽略的文件时，核对 glob 与生成脚本的输出路径一致即可。
- **rule 的 frontmatter `---` 必须是文件第一行**，否则 `paths` 不生效，rule 变成常驻。
- **CLAUDE.md 一条一行，不带原因。** 能用 `paths` 限定触发条件的一律走 rule 或注释；带"因为/当初/以前"的先拆开，原因再走一遍阶梯。确有扩展内容的，同一行末尾留指针（"改 X 前读 …"）。
- **单个文件的内容写注释，不写 rule。** `paths` 只匹配一个文件的 rule，只在那个文件没法写注释时才用。
- **rule 正文"做什么"在前，一两句原因跟在后面。** 正文不超过 10 行（不算 frontmatter 和空行），超出时按「扩展内容与指针」拆，正文留指针。
- **一件事只写一处。** 同一件事散在两个文件里比记在一个长文件里更糟。
- **新建前先查重。** 新建 rule、skill、文档前，按 slug 和主题关键词 grep **整个仓库所有作用域**的 `.claude/`、`context-docs/`、CLAUDE.md。有同主题的就改那份，不新建；它在别的作用域、而这次内容让归属变了的，照样改那份，挪动交给 organize-context。
- **代码注释守本分**：只收"读这段代码的人此刻需要知道的"，1–3 行：做什么、坑、一句原因，紧贴相关代码。试过的方案、数字、长篇原因过了「准入门槛」的进文档，注释里留指针（见「扩展内容与指针」）；经过、流水直接删。讲"这段代码在做什么、怎么用"的注释不受限制。
- **不碰用户级配置**：不改 `~/.claude/CLAUDE.md`、`~/.claude/settings.json`。

## hook

插件带三个 hook，都可以用环境变量关掉：

- **comment-hook**（PostToolUse，`CONTEXT_KEEPER_COMMENT_HOOK=0` 关闭）：Claude 新写了 4 行以上（超过注释的 3 行上限）的独立注释块时提醒它：注释只留必须知道的那一句；扩展内容先过「准入门槛」，经过、流水、推导直接删，过了的才进文档、原处留指针。只提醒，不阻断。
- **doc-hook**（PostToolUse，`CONTEXT_KEEPER_DOC_HOOK=0` 关闭）：Claude 改了 `context-docs/` 里的文档（文档入口不算）之后，列出指到这份文档的行，提醒它：这次改动让哪一行的重点不再成立，同一次改动里把那一行也改掉。指到它的行按检查脚本的口径找：rule（含领域索引 rule）、文档入口、CLAUDE.md、skill 里代码块外的行，以及源码注释里解析得到这份文档的路径；别的文档里的互相引用、其他 Markdown 和代码块里的示例、源码字符串里的路径不算。最多列 10 处，其余给出数目。只提醒，不阻断。每次改文档都提醒，但同一会话里同一份文档的清单只给一次：之后再改它、清单没变时只提醒一行，清单变了或主会话压缩上下文之后重新给（主会话和每个子代理各算各的）；没有任何一处指到的文档（比如刚新建、还没登记的）不提醒。用 git grep 找，不是 git 仓库的项目不提醒。
- **pointer-guard**（PreToolUse，`CONTEXT_KEEPER_POINTER_HOOK=0` 关闭）：Claude 要改的代码附近有指向 `context-docs/` 文档的注释指针、而本会话还没读过那份文档时，拦下这次编辑，把指针原文给它看，让它按触发条件决定先读文档还是直接重试，并提醒它改完后同步过时的重点和文档。同一会话里每处指针只拦一次（同一份文档被几处指到的，各拦各的），文档读过之后指向它的指针都不再拦。读过指 Read 成功，或 Bash 里用 cat / head / tail 这类命令读过；读失败、`git add` 这类只是提到路径的不算。主会话压缩上下文后，拦过、读过都重新算。和拦下它的那次编辑在同一条消息里的后几个 Edit 继续拦：它们是挨个执行的，提交时 Claude 还没看到拦截消息；Claude 看到消息后重新提交的那次放行（查不到消息 id 时退回按时间算，拦下后 3 秒内继续拦）。主会话和每个子代理各算各的，主会话读过、被拦过，子代理第一次改到时照样拦。"附近"指：改动范围内、外层函数 / 类的声明行、紧贴在它们上方的注释和紧跟在下面的 docstring，以及文件头注释。行注释、块注释（含 JSX 的 `{/* */}`）、Python docstring 里的指针都认；写在字符串或行尾注释里的不保证拦得到。文件头注释指文件开头、后面是空行或 import 的那几段（开头的 shebang、PHP 的 `<?php`、`'use client'` 这类指令、Vue / Svelte 的 `<script>` 标签不算代码，跳过）；紧贴着第一个声明的注释算那个声明的，所以涉及整个文件的指针写在文件头时，和下面的代码之间空一行。只认非 Markdown 文件里的指针，rule 和 CLAUDE.md 里的不管。指针按项目根起的路径解析：项目根取离文件最近的 `.git`，不是 git 仓库时取启动会话的目录。

## 检查脚本

能确定性校验的部分交给脚本，不要再手工逐条核对：

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/check.mjs" [路径] [--comments]
```

检查：rule 的 frontmatter 位置、缺 `paths`、glob 匹配不到文件 / 基准错位 / 过宽、正文超过 10 行、只匹配一个能写注释的文件（认得出是生成物或 lockfile 的不报）；skill 缺 description；CLAUDE.md 和 rule 里的 `@` import；CLAUDE.md 疑似带原因的行；文档文件名（日期/编号前缀、非 slug）、嵌套领域目录、缺领域索引 rule（已被 rule、CLAUDE.md 或代码注释指到的文档不算）；`context-docs/README.md` 没被根 CLAUDE.md 指到；失效指针（只查 CLAUDE.md、rule、skill、`context-docs/` 文档和源码里的注释，代码块里的示例不算；纯文本路径按仓库根解析，Markdown 链接的目标按所在文件的目录解析，链接目标写成仓库根起的路径的报出来并给出改好的相对路径，链接文字和链接目标指向不同文档的也报；源码字符串里、脚本不认得的非 Markdown 文件里指得到文档的路径算已登记，指不到的不报）；没写"什么时候读"的指针；没有重点的登记行（领域索引 rule、文档入口里以路径开头的行，以及正文只有这种行的 rule；路径前面有话的不报，那句话是文档标题还是重点脚本不判断）；孤儿文档（没登记在任何入口、rule、CLAUDE.md 或代码里）；`context-docs/`、`.claude/rules/`、`.claude/skills/` 被 `.gitignore` 忽略；放在 `.claude/` 下或按类型分目录的文档。`context-docs/` 是否已被别的用途占用查不出来，要人工看。`--comments` 额外列出长注释块（4 行以上）和带信号词的注释作为搬运候选，3 行以内、已经带着有效指针的注释不列。带路径时只报告该路径下文件的问题；路径相对当前目录找不到时，按仓库根起的路径再找一次；路径在别的 git 仓库里时，检查那个仓库。

**修剪候选**另列一块，按「准入门槛」找该删的东西，不计入错误、警告的计数，也不影响退出码：

- 空壳文档：代码块外、独立成行的占位行（`未记录`、`暂无`、`待补充`、`TBD`、`TODO`，前面可以带「背景：」这种标签）有两处以上；表格单元格里的不算
- 已取代的文档：状态行写着取代、推翻、废弃、作废、撤销、弃用
- 决策日志形态：第一个标题以编号（`0029：`）或日期（`2026-09-25 ·`）开头，或者正文按编号互相引用（`[0035]`、「推翻 0039」）；以及「旧编号 → 文件」的对照表（表格里第一格是编号的行有 5 行以上）
- 过宽的 rule：`paths` 超过 10 项（按逗号切开，花括号不展开；领域索引 rule 不算）。超过 10 项的，基本都是把几组「改 A 同步 B」攒成了一张表，碰到其中一个文件，其余的行也全跟着进来
- 强调泛滥（提示）：一条 rule 的正文里 ⚠ 和加粗加起来超过两处

输出开头有每个作用域的规模：rule 条数和正文行数（不算 frontmatter 和空行）、文档数、指针数（CLAUDE.md、rule、skill、文档入口、源码注释里指向文档的行；文档之间的互相引用不算）。体检前后各跑一次，对比修剪的效果。

脚本的判断是机械的：「警告」「提示」要结合上下文看（比如 glob 指向的生成物、确实该常驻的 rule），「错误」基本都要处理。有错误时退出码为 1。`node` 不可用时按本规范手工检查。脚本没有依赖，用户想接进 CI 时把 `check.mjs` 连同 `lib/` 目录一起复制进项目。

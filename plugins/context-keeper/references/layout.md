# context-keeper 规范

`organize-context` 和 `record-context` 共用这份规范。目标：**常驻 context 尽量小，其余按需加载；读代码得不到的背景挂在它所属的代码路径上（rule），rule 装不下或挂不上代码的才进项目文档（`.context/`），不散在 CLAUDE.md 和代码注释里。**

## 加载机制（2026-09 已核实，直接按此执行；实际观察与某条矛盾时以观察为准，并在计划或报告里指出）

1. `.claude/rules/` 下的 `.md`（递归发现，可用子目录组织）带 `paths:` glob → 只有读/改到匹配文件时才进 context。没有 `paths` 的 rule 常驻，`paths` 只有 `"**"` 的也常驻。`paths` 可以是列表或逗号分隔的字符串，支持花括号（`*.{ts,tsx}`），按 **gitignore 语义**匹配：不含 `/` 的模式（`*.test.ts`）匹配任意深度；含 `/` 的相对作用域根锚定；匹配到目录就等于匹配目录下所有文件，所以 `src/api`、`src/api/**` 等价，`src/*` 等于整个 `src/`；`./` 开头的匹配不到任何文件（2026-11 读 Claude Code 2.1.319 源码核实）。
2. 子目录里的 `CLAUDE.md` → 碰到那个目录的文件时才加载，但**一旦触发是整文件加载**，也不支持 `paths:`。
3. Skill → 启动时只加载 description。子包的 `.claude/skills/` 也有效，碰到该包的文件后才可用，重名时用 `apps/web:deploy` 这种目录限定名。
4. 子包的 `.claude/rules/` 同样有效，**`paths` 相对该子包解析**（官方文档没写，已实测）。
5. **`@path` import 是 eager 的**，启动就展开进 context，完全不省 token。**禁止**用它来"拆分"。
6. 自动记忆在 `~/.claude/projects/<project>/memory/`，不在仓库里，只对当前用户、当前机器生效；`MEMORY.md` 前 200 行常驻。

由此得出两点：

- **根 CLAUDE.md 和目录级 CLAUDE.md 都要瘦**。根的常驻；目录级的触发即全量——一个 400 行的包级 CLAUDE.md，碰了包里任意一个文件就全进来。
- **带 `paths` 的 rule 命中就一定被看到，项目文档要 Claude 自己决定去读。** 所以能挂到代码上的背景优先直接写进 rule（见「rule 还是文档」）；进了 `.context/` 的文档必须登记在一个入口上，光写进去等于没写（见「项目文档」）。

## 仓库形态与作用域

### 判断形态

命中下列任一信号即为 **monorepo**，否则为**单仓库**：

- `pnpm-workspace.yaml`、根 `package.json` 的 `workspaces`、`lerna.json`、`nx.json`、`turbo.json`、`rush.json`
- `Cargo.toml` 的 `[workspace]`、`go.work`、`settings.gradle(.kts)` 的 `include`、`pom.xml` 的 `<modules>`
- 以上都没有，但有多个带独立清单文件且各自构建的目录——拿不准，说明依据，让用户确认

**包**是 workspace 配置实际匹配到的成员目录，以配置为准，不凭目录名猜。

### 作用域

**作用域**是一套 `CLAUDE.md` + `.claude/` + `.context/` 的挂载点：单仓库只有仓库根一个；monorepo 是仓库根加每个包。包的 `.claude/`、`.context/` 只在真有内容时才建。

- 内容涉及的文件全在某个包内 → 该包；涉及两个及以上包 → 根；单仓库 → 一律根。
- `.claude/` 只放 Claude Code 要从这里加载的东西。本规范往里写的只有 `rules/`、`skills/`；已有的 `settings*.json`、`commands/`、`agents/`、hook 脚本等原样保留。
- 根 CLAUDE.md 可以是 `CLAUDE.md` 或 `.claude/CLAUDE.md`，两者等价；两个都存在时交给用户决定是否合并。
- 项目文档放 `.context/`。**不放 `.claude/`**：Claude 偶尔会把 `.claude/` 下的文件当成敏感配置而拒绝编辑。**不用不带点的 `context/`**：这个名字常被项目代码占用。
- `.context/` 是点开头的目录，有些工具默认跳过它：Grep / Glob 时显式传 `.context/` 作为 path。它必须进 git：被 `.gitignore` 忽略、或已被别的用途占用（有被代码或工具读取的文件）时不往里写，交给用户决定。

### 目录级 CLAUDE.md

单仓库的子目录（如 `src/server/CLAUDE.md`）或包内更深层的 CLAUDE.md，按包级同样的标准瘦身：只留"该目录内任何任务都适用"的。**不要**在这些目录下另建 `.claude/` 或 `.context/`，拆出来的东西放进所属作用域。**不要**为了放某条规则新建目录级 CLAUDE.md，没有的走 rule。

## 标签与去处

| 标签 | 判据 | 去处 |
|---|---|---|
| `ALWAYS` | 任何任务都可能违反的硬约束（commit 规则、语言/风格约定、绝对禁止做的事） | 全仓通用 → 根 `CLAUDE.md`；只在某包 / 某个已有目录级 CLAUDE.md 所在目录内成立、且其中任何任务都适用 → 那个 CLAUDE.md。一条一行 |
| `HOOK` | 能被脚本/lint/CI 确定性校验的 | 建议改成 hook 或 lint。**只提建议，不自己改 CI**。检查落地前文字不删，继续按阶梯归类放好 |
| `PATH-RULE` | 只在碰到特定文件、目录或文件类型时才需要知道的内容："做什么"（"改 A 必须同步 B"、某模块的坑、某类文件的约定），连同它的原因、经过、数字 | `<作用域>/.claude/rules/<领域>/<name>.md`。背景放不下时拆一份 `DOC`（见「rule 还是文档」） |
| `SKILL` | 有步骤的流程（发布、迁移、排障 playbook），平时不需要 | `<作用域>/.claude/skills/<name>/SKILL.md` |
| `DOC` | 读代码得不到、rule 又装不下的背景：一是**能挂到代码上、但太长**的（多段的设计权衡、实测数字的历史表格、外部系统调研、几条 rule 共用的背景）；二是**挂不到具体代码上**的（评估过但没做的需求、外部系统的限制、还没有对应代码的决定、领域知识） | `<作用域>/.context/<领域>/<slug>.md`。第一种登记进领域索引 rule，第二种登记进 `<作用域>/.context/README.md`（见「项目文档」） |
| `DERIVABLE` | 删掉也不会让 Claude 犯错的：读代码就能知道的，以及只是复述某次需求做了什么的（commit 的职责） | **删除** |
| `STALE` | 已不成立、与现状矛盾、或引用了不存在的文件 | **删除**，单独列出让用户确认 |
| `PERSONAL` | 个人偏好、对 Claude 的纠正、个人工作习惯 | 不进仓库，留在自动记忆。想对所有项目生效时，给出可粘贴到 `~/.claude/CLAUDE.md` 的文本，**不直接改那个文件** |
| `ENV-BOUND` | 换台电脑、网络、操作系统就不成立的：本机路径、本机版本、端口占用、代理/网络、只在某台机器出现的怪现象、凭据 | 不进仓库，留在自动记忆 |

有条件成立的（"在 macOS 上 X 会失败"、"Node 20 以下会报 Y"）不算 `ENV-BOUND`：换台同类环境照样遇到。按上表正常归类，**正文第一行写明适用条件**（如"仅 macOS："）。

**敏感信息一律不进仓库**，不论原本是什么标签：API key / token / 密码 / 私有仓库地址 / 内网 IP 或域名 / 含用户名的绝对路径 / 任何用户没打算公开的信息。向用户报告时只说类型和位置，不打出值本身。

## 判据阶梯

按顺序问，第一个"是"就停。一条内容混着"做什么"和"为什么/数字/背景"时，**能挂到代码上的不拆**，一起写进同一条 rule；只有"做什么"要进 CLAUDE.md、或背景在 rule 里放不下时，才把背景拆出来再走一遍阶梯。

0. 它属于这个项目吗？个人偏好 → `PERSONAL`；换台机器就不成立 → `ENV-BOUND`
1. 删掉它，Claude 会不会犯错？不会 → `DERIVABLE`。读代码能直接看出来的、只是复述某次改动的，都算不会。反过来，以后做事用得上的原因、约束、数字，哪怕 commit message 里写过，也算会——Claude 平时不翻 git 历史
2. 能写成脚本自动校验吗？能 → 同时打上 `HOOK`，但**不停**，继续往下问，定出检查落地前文字放哪
3. 有步骤、平时用不上吗？是 → `SKILL`
4. 只在碰到特定文件、目录或文件类型时才需要知道吗？"做什么"、坑、原因、数字都算。是 →
   - 是适用于某个已有目录级 CLAUDE.md 所在目录内任何任务的"做什么" → `ALWAYS`，放进那个 CLAUDE.md；它的原因拆出来再走一遍
   - 否则 → `PATH-RULE`，原因直接写在 rule 正文里；放不下时（见「rule 还是文档」）把背景拆成 `DOC`，登记进领域索引 rule

   这一步要严格：能挂到代码上的都挂上。
5. 是背景（原因、经过、数字、外部约束、评估过但没做的需求），但挂不到具体代码上吗？是 → `DOC`，登记进 `.context/README.md`
6. 剩下的"做什么"才是 `ALWAYS`

## rule 还是文档

能挂到代码上的内容，**默认写进 rule**，"做什么"在前，原因、经过、数字跟在后面。命中就一定被看到，也不用维护文档、索引行和指针。只有下面几种情况才把背景拆成文档，rule 里留"做什么"和一行文档路径：

- rule 正文（不算 frontmatter 和空行）会超过 20 行
- 实测数字的历史表格：会一直追加。rule 里可以写当前值
- 同一段背景要被几条 `paths` 不同的 rule 共用：一件事只写一处

背景只和 `paths` 匹配到的一小部分文件有关时，先把 `paths` 收窄，或者拆成几条更窄的 rule，而不是把背景挪进文档。

## 项目文档

### 位置与命名

- 路径：`<作用域>/.context/<领域>/<slug>.md`。涉及两个及以上领域、或说不清属于哪块的，放 `.context/` 顶层。
- **领域**指"讲的是系统哪一块"（`api`、`db`、`styling`），取自项目已有叫法：优先用同作用域 `.claude/rules/<领域>/` 已在用的名字，其次用代码里的模块名、目录名，不自造。rules 和 `.context/` 共用同一套领域名。**第一份文档就放进领域目录**，只分一层，不嵌套。
- **不按信息类型分目录**（不建 `decisions/`、`data/`、`pitfalls/`）：要改支付模块时，想看的是支付相关的一切，不管它是原因、数字还是坑。
- `.context/README.md`（只认作用域 `.context/` 顶层这一个）是文档入口，不是文档，见「入口」。
- 文件名 `<slug>.md`：英文小写短横线，概括主题（`retry-policy`，不是 `fix-bug`）。**不带日期、不带编号**：文档描述现状、原地更新，创建日期没有意义；两个分支为同一主题各建一份时，同名文件会在合并时冲突，正好把重复暴露出来。

### 入口

文档不会自动加载，每份都要登记在至少一个入口上，否则基本不会被读到。入口有两种，按文档能不能挂到代码上选：

| 文档 | 入口 | 什么时候被看到 |
|---|---|---|
| 能挂到代码上（rule 装不下的长背景） | 领域索引 rule `<作用域>/.claude/rules/<领域>/context-index.md` | 碰到这个领域的代码时 |
| 挂不到代码上（评估过但没做的需求、外部系统限制、还没有代码的决定） | 文档入口 `<作用域>/.context/README.md`，由根 CLAUDE.md 常驻一行指过去 | 做新需求、评估方案前 |
| 两个时候都要看到的（见下文「两边都登记」） | 两个入口都登记 | 两者 |

两种入口的正文都是每份文档一行：**仓库根起的路径** + 一句"什么时候该读"（模板见 templates.md）。不要把文档内容抄进入口。

**领域索引 rule**：每个有这类文档的领域一个，`paths` 覆盖这个领域的代码。碰到该领域的代码时，文档清单随 rule 自动进 context，成本只有几行；文档正文仍按需读。顶层的跨领域文档，登记进每个相关领域的索引。

**文档入口**：每个有这类文档的作用域一个 `.context/README.md`。它是挂不上 `paths` 的知识唯一的触发点，所以根 CLAUDE.md 的「更多上下文」里必须有一行，写明所有作用域的 `.context/README.md` 路径（包级 CLAUDE.md 碰到包里的文件才加载，等不到"提需求"的时候）。

**两边都登记**：一份文档在"改代码时"和"评估新需求时"都要被看到，就同时登记进领域索引 rule 和 `.context/README.md`，两行各写各的"什么时候该读"。登记行只是指针，不算"一件事写两处"。典型的有：

- 挂得到代码上、但评估需求时也要考虑的：安装包体积、性能预算、外部系统的配额和限流——"做这个功能会不会超"在动代码之前就要知道
- 挂不到代码上、但和某个领域的代码也有关系的：某模块评估过但没做的功能，改那个模块时也值得看一眼

只在改代码时才用得上的文档不进 `.context/README.md`：它是每次做新需求都要过一遍的清单，越短越好。

新建、改名、删除文档时同步改入口。

### 内容

- **按主题组织，不按需求组织。**"这次做了什么"由 commit 记录，不要每做一个需求就落一个文档。一个主题一份，优先改已有的同主题文档。
- 第一行是标题，说清讲的是什么。没有固定模板，怎么分节按内容定。
- **写的是现状。** 情况变了就原地改写，不追加"更新：……"，不另建新文件再把旧的标成作废。旧说法交给 git；以后还用得上的历史留在正文里：
  - 被放弃的方案只在"怕以后有人重新提"时才留，一两句话写明放弃了什么、为什么。
  - 评估过但没做的需求：写明卡在哪（哪个外部系统、什么限制）、评估的时间，以及什么条件变了值得重新评估。
  - **实测数字**：每个都带测出它的日期和测法；迁移来的原文没写就标 `未记录`，不编造。同一指标测出新值时追加一行（表格见模板），不覆盖旧值；被测的东西已经没了才删。
- 文档只写背景。能挂到代码上的"做什么"写成 rule，rule 正文里留一行路径指向文档。

### 移动、改名、删除

会让指向它的入口（领域索引 rule、`.context/README.md`）、其他 rule、代码指针、CLAUDE.md 失效。先在**整个仓库** grep 旧路径找出所有指针，一并改掉；整份删掉的把指针行一起删。有指针落在本次不可写的文件里，就不动这份文档，只提建议。移动和改名只在 organize-context 里做，record-context 不挪已有文件。

## 硬约束

- **禁止 `@` import**，指路一律用自然语言写**仓库根起的路径**（方便 grep 和脚本校验）。
- **`paths` 要窄到能真正起过滤作用。** 不许写 `**/*`、`src/**`、`src/*`、`packages/**` 这种一碰作用域就全中的；领域级的 `src/api/**` 可以。glob 相对 rule 所属作用域的根写（包内 rule 相对包目录，根 rule 从仓库根写完整路径），必须至少匹配到一个现存文件。例外：指向生成物或被 `.gitignore` 忽略的文件时，核对 glob 与生成脚本的输出路径一致即可。
- **rule 的 frontmatter `---` 必须是文件第一行**，否则 `paths` 不生效，rule 变成常驻。
- **CLAUDE.md 一条一行，不带原因。** 能用 `paths` 限定触发条件的一律走 rule；带"因为/当初/以前"的先拆开，原因再走一遍阶梯（能挂到代码上的进 rule，挂不上的进文档）。
- **rule 正文"做什么"在前，原因跟在后面。** 正文不超过 20 行（不算 frontmatter 和空行），超出时按「rule 还是文档」拆，正文留一行路径。
- **一件事只写一处。** 同一件事散在两个文件里比记在一个长文件里更糟。
- **新建前先查重。** 新建 rule、skill、文档前，按 slug 和主题关键词 grep **整个仓库所有作用域**的 `.claude/`、`.context/`、CLAUDE.md。有同主题的就改那份，不新建；它在别的作用域、而这次内容让归属变了的，照样改那份，挪动交给 organize-context。
- **代码注释守本分**：只收"读这段代码的人此刻需要知道的"。背景（历史沿革、数字、长篇原因）写进 `paths` 指向这个文件的 rule，放不下的进文档。原处要不要留指针：
  - 这个位置确有讲究（顺序不能换、数值不能随便改）→ 留一行，说清讲究 + 原因所在文件的路径（rule 或文档），给不用 Claude 读代码的人看：

    ```ts
    // 重试次数不能超过 3，原因见 apps/web/.claude/rules/api/retry.md
    ```

  - 纯背景、没有"此处别乱动"的意思 → 不留，碰到这个文件时 rule 会自动加载。
  - 不留 `// 见文档` 这种没有信息量的话。
- **不碰用户级配置**：不改 `~/.claude/CLAUDE.md`、`~/.claude/settings.json`。

## 检查脚本

能确定性校验的部分交给脚本，不要再手工逐条核对：

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/check.mjs" [路径] [--comments]
```

检查：rule 的 frontmatter 位置、缺 `paths`、glob 匹配不到文件 / 基准错位 / 过宽、正文超过 20 行；skill 缺 description；CLAUDE.md 和 rule 里的 `@` import；CLAUDE.md 疑似带原因的行；文档文件名（日期/编号前缀、非 slug）、嵌套领域目录、缺领域索引 rule；`.context/README.md` 没被根 CLAUDE.md 指到；失效指针；孤儿文档（没登记在任何入口、rule、CLAUDE.md 或代码里）；`.context/` 被 `.gitignore` 忽略；放在 `.claude/` 下或按类型分目录的文档。`--comments` 额外列出长注释块和带信号词的注释作为搬运候选。带路径时只报告该路径下文件的问题。

脚本的判断是机械的：「警告」「提示」要结合上下文看（比如 glob 指向的生成物、确实该常驻的 rule），「错误」基本都要处理。有错误时退出码为 1。`node` 不可用时按本规范手工检查。脚本没有依赖，用户想接进 CI 时可以复制进项目。

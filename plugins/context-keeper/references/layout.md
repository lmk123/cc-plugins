# context-keeper 规范

`organize-context` 和 `record-context` 共用这份规范。目标：**常驻 context 尽量小，其余按需加载。** 读代码得不到的知识放在离用到它的代码最近、又不会被无关任务读到的地方：

- 只和一个文件（或其中一段代码）有关的，写成**代码注释**，紧贴相关代码，简短；
- 几个文件共用的，写成带 `paths` 的 **rule**；
- 任何任务都可能违反的硬约束，才进 **CLAUDE.md**；
- 以上三处需要的**扩展内容**（历史决策、试过的方案、实测数据、坑的详细经过、外部系统调研），以及挂不到代码上的背景，进**项目文档**（`.context/`）。原处只留「一句话重点 + 什么时候读 + 路径」的指针，由 Claude 按需读。

## 加载机制（2026-09 已核实，直接按此执行；实际观察与某条矛盾时以观察为准，并在计划或报告里指出）

1. `.claude/rules/` 下的 `.md`（递归发现，可用子目录组织）带 `paths:` glob → 只有读/改到匹配文件时才进 context。没有 `paths` 的 rule 常驻，`paths` 只有 `"**"` 的也常驻。`paths` 可以是列表或逗号分隔的字符串，支持花括号（`*.{ts,tsx}`），按 **gitignore 语义**匹配：不含 `/` 的模式（`*.test.ts`）匹配任意深度；含 `/` 的相对作用域根锚定；匹配到目录就等于匹配目录下所有文件，所以 `src/api`、`src/api/**` 等价，`src/*` 等于整个 `src/`；`./` 开头的匹配不到任何文件（2026-11 读 Claude Code 2.1.319 源码核实）。
2. 子目录里的 `CLAUDE.md` → 碰到那个目录的文件时才加载，但**一旦触发是整文件加载**，也不支持 `paths:`。
3. Skill → 启动时只加载 description。子包的 `.claude/skills/` 也有效，碰到该包的文件后才可用，重名时用 `apps/web:deploy` 这种目录限定名。
4. 子包的 `.claude/rules/` 同样有效，**`paths` 相对该子包解析**（官方文档没写，已实测）。
5. **`@path` import 是 eager 的**，启动就展开进 context，完全不省 token。**禁止**用它来"拆分"。
6. 自动记忆在 `~/.claude/projects/<project>/memory/`，不在仓库里，只对当前用户、当前机器生效；`MEMORY.md` 前 200 行常驻。

由此得出几点：

- **根 CLAUDE.md 和目录级 CLAUDE.md 都要瘦**。根的常驻；目录级的触发即全量——一个 400 行的包级 CLAUDE.md，碰了包里任意一个文件就全进来。
- **只匹配一个文件的 rule，和写在那个文件里的注释成本一样**：碰到文件就整条加载，Claude 只读文件的一部分时也一样。它比注释差在离代码远、定位不到函数，所以单个文件的内容写成注释；rule 留给几个文件共用的内容，以及没法写注释的文件（见「标签与去处」）。
- **写在原处的内容一定被看到，项目文档要 Claude 自己决定去读。** 所以必须知道的那一句（坑、约束）留在原处，只有扩展内容进文档；指针要写清"什么时候读"，Claude 才判断得准（见「指针」）。改代码时还有 `pointer-guard` hook 兜底（见「hook」）。进了 `.context/` 的文档必须至少被一处指到，光写进去等于没写（见「项目文档」）。

## 仓库形态与作用域

### 判断形态

命中下列任一信号即为 **monorepo**，否则为**单仓库**：

- `pnpm-workspace.yaml`、根 `package.json` 的 `workspaces`、`lerna.json`、`nx.json`、`turbo.json`、`rush.json`
- `Cargo.toml` 的 `[workspace]`、`go.work`、`settings.gradle(.kts)` 的 `include`、`pom.xml` 的 `<modules>`
- 以上都没有，但有多个带独立清单文件且各自构建的目录——拿不准，说明依据，让用户确认

**包**是 workspace 配置实际匹配到的成员目录，以配置为准，不凭目录名猜。

### 作用域

**作用域**是一套 `CLAUDE.md` + `.claude/` + `.context/` 的挂载点：单仓库只有仓库根一个；monorepo 是仓库根加每个包。包的 `.claude/`、`.context/` 只在真有内容时才建。

- 内容涉及的文件全在某个包内 → 该包；涉及两个及以上包 → 根；单仓库 → 一律根。
- `.claude/` 只放 Claude Code 要从这里加载的东西。本规范往里写的只有 `rules/`、`skills/`；已有的 `settings*.json`、`commands/`、`agents/`、hook 脚本等原样保留。
- 根 CLAUDE.md 可以是 `CLAUDE.md` 或 `.claude/CLAUDE.md`，两者等价；两个都存在时交给用户决定是否合并。
- 项目文档放 `.context/`。**不放 `.claude/`**：Claude 偶尔会把 `.claude/` 下的文件当成敏感配置而拒绝编辑。**不用不带点的 `context/`**：这个名字常被项目代码占用。
- `.context/` 是点开头的目录，有些工具默认跳过它：Grep / Glob 时显式传 `.context/` 作为 path。它必须进 git：被 `.gitignore` 忽略、或已被别的用途占用（有被代码或工具读取的文件）时不往里写，交给用户决定。
- `.claude/rules/`、`.claude/skills/` 同样必须进 git。不少项目把 `.claude/` 整个忽略，或只放行 `settings.json`：这时写进去的 rule、skill 只在本机生效，队友看不到。新建前用 `git check-ignore` 确认，被忽略就交给用户调整 `.gitignore`（通常只需要忽略 `settings.local.json`）。

### 目录级 CLAUDE.md

单仓库的子目录（如 `src/server/CLAUDE.md`）或包内更深层的 CLAUDE.md，按包级同样的标准瘦身：只留"该目录内任何任务都适用"的。**不要**在这些目录下另建 `.claude/` 或 `.context/`，拆出来的东西放进所属作用域。**不要**为了放某条规则新建目录级 CLAUDE.md，没有的走 rule。

## 标签与去处

| 标签 | 判据 | 去处 |
|---|---|---|
| `ALWAYS` | 任何任务都可能违反的硬约束（commit 规则、语言/风格约定、绝对禁止做的事） | 全仓通用 → 根 `CLAUDE.md`；只在某包 / 某个已有目录级 CLAUDE.md 所在目录内成立、且其中任何任务都适用 → 那个 CLAUDE.md。一条一行，有扩展内容时同一行末尾加指针 |
| `HOOK` | 能被脚本/lint/CI 确定性校验的 | 建议改成 hook 或 lint。**只提建议，不自己改 CI**。检查落地前文字不删，继续按阶梯归类放好；落地后由用户删，或 organize-context 体检时列出来 |
| `COMMENT` | 只和**一个文件**（或其中一个函数、一段代码）有关、且这个文件能写注释的："做什么"（"这个值不能超过 3"、"顺序不能换"）、坑、一句原因 | 代码注释，紧贴相关代码：函数 / 常量上方，涉及整个文件的写在文件头。1–3 行。扩展内容拆成 `DOC`，注释里留指针 |
| `PATH-RULE` | 只在碰到特定文件时才需要知道、但**涉及多个文件**的：一类文件的约定、一个目录的坑、"改 A 必须同步 B"；以及只涉及一个文件、但这个文件**没法写注释**的（JSON、lockfile、生成物、二进制资源，或写了会被工具覆盖） | `<作用域>/.claude/rules/<领域>/<name>.md`。"做什么"加一两句原因，正文不超过 10 行。扩展内容拆成 `DOC`，rule 里留指针 |
| `SKILL` | 有步骤的流程（发布、迁移、排障 playbook），平时不需要 | `<作用域>/.claude/skills/<name>/SKILL.md` |
| `DOC` | 读代码得不到、原处又不该展开的：一是**扩展内容**，即注释、rule、CLAUDE.md 里那一句话之外的部分（历史决策、试过又放弃的方案、实测数字和它的历史、坑的详细经过、外部系统调研）；二是**挂不到具体代码上**的（评估过但没做的需求、外部系统的限制、还没有对应代码的决定、领域知识） | `<作用域>/.context/<领域>/<slug>.md`。第一种由原处的指针登记（注释、rule 或 CLAUDE.md 里那一行），领域里多处都该知道、又不属于某一处的登记进领域索引 rule；第二种登记进 `<作用域>/.context/README.md`（见「项目文档」） |
| `DERIVABLE` | 删掉也不会让 Claude 犯错的：读代码就能知道的，以及只是复述某次需求做了什么的（commit 的职责） | **删除** |
| `STALE` | 已不成立、与现状矛盾、或引用了不存在的文件 | **删除**，单独列出让用户确认 |
| `PERSONAL` | 个人偏好、对 Claude 的纠正、个人工作习惯 | 不进仓库，留在自动记忆。想对所有项目生效时，给出可粘贴到 `~/.claude/CLAUDE.md` 的文本，**不直接改那个文件** |
| `ENV-BOUND` | 换台电脑、网络、操作系统就不成立的：本机路径、本机版本、端口占用、代理/网络、只在某台机器出现的怪现象、凭据 | 不进仓库，留在自动记忆 |

有条件成立的（"在 macOS 上 X 会失败"、"Node 20 以下会报 Y"）不算 `ENV-BOUND`：换台同类环境照样遇到。按上表正常归类，**正文第一行写明适用条件**（如"仅 macOS："）。

**敏感信息一律不进仓库**，不论原本是什么标签：API key / token / 密码 / 私有仓库地址 / 内网 IP 或域名 / 含用户名的绝对路径 / 任何用户没打算公开的信息。向用户报告时只说类型和位置，不打出值本身。

## 判据阶梯

按顺序问，第一个"是"就停。一条内容混着"做什么"和"为什么 / 经过 / 数字"时，先拆成两部分：**必须知道的那一句**（做什么、坑，加一句原因）按阶梯定去处；**扩展内容**（第二句以后的原因、经过、数字）是 `DOC`，原处留指针（见「扩展内容与指针」）。整条两三行就说完的不拆，原样写在去处。

0. 它属于这个项目吗？个人偏好 → `PERSONAL`；换台机器就不成立 → `ENV-BOUND`
1. 删掉它，Claude 会不会犯错？不会 → `DERIVABLE`。读代码能直接看出来的、只是复述某次改动的，都算不会。反过来，以后做事用得上的原因、约束、数字，哪怕 commit message 里写过，也算会——Claude 平时不翻 git 历史
2. 能写成脚本自动校验吗？能 → 同时打上 `HOOK`，但**不停**，继续往下问，定出检查落地前文字放哪
3. 有步骤、平时用不上吗？是 → `SKILL`
4. 只在碰到特定文件、目录或文件类型时才需要知道吗？是 →
   - 适用于某个已有目录级 CLAUDE.md 所在目录内任何任务 → `ALWAYS`，放进那个 CLAUDE.md
   - 适用于某个包内任何任务（monorepo）→ `ALWAYS`，放进那个包的 CLAUDE.md（没有就新建），不写成覆盖整个包的宽 rule
   - 只涉及一个文件、且这个文件能写注释 → `COMMENT`，写在相关的函数、常量上方；涉及整个文件的写在文件头
   - 否则（涉及多个文件，或文件没法写注释）→ `PATH-RULE`

   "涉及几个文件"按**谁需要知道**算，不按这条知识讲的是哪个文件算。约束的是调用方的（"必须在 X 之后调用""返回值不能缓存"），需要知道的是调用它的那些文件，写在定义上方的普通注释里，写调用代码时不一定读得到：调用方分散的，写进定义处的 API 文档注释（JSDoc / docstring，属于"怎么用"，查定义、IDE 悬停时看得到，不受 1–3 行限制）；调用方集中在某个目录的，写成 `paths` 覆盖调用方的 `PATH-RULE`。

   这一步要严格：能挂到代码上的都挂上，能挂到一个文件上的不写成 rule。
5. 是背景（原因、经过、数字、外部约束、评估过但没做的需求），但挂不到具体代码上吗？是 → `DOC`，登记进 `.context/README.md`
6. 剩下的"做什么"才是 `ALWAYS`

## 扩展内容与指针

### 什么时候拆

注释、rule、CLAUDE.md 里只放**必须知道的那一句**：做什么、坑，加一句原因。超出的部分拆进文档，原处留指针：

- 注释超过 3 行，或要讲经过、试过的方案、数字
- rule 正文（不算 frontmatter 和空行）会超过 10 行
- 实测数字和它的历史：会一直追加。原处可以写当前值
- 同一段背景要被几处共用（几条 rule、几个文件的注释）：一件事只写一处

两三行就说完的不拆，直接写在原处。为了格式统一硬拆成"一句话 + 指针"，只会多一次读文件。

### 指针怎么写

指针是原处的一行：**重点 + 什么时候读 + 仓库根起的路径**，可以在括号里写文档里有什么。

```ts
// 重试上限 3：网关连续 5 次失败会封 IP 10 分钟。改重试次数或退避前读 apps/web/.context/api/retry-policy.md（事故经过、试过的熔断方案）
```

- **重点**：坑、约束类的必须写，写成照着做就不会出错的结论。这样 Claude 没去读文档也不会踩坑，漏掉的只是细节。纯历史、纯数据（没有"此处别乱动"的意思）的可以省掉。
- **什么时候读**：写成动作（"改 X 前""要调 Y 时""评估 Z 前"），不写成话题（"X 的背景见""原因见"）。Claude 能拿动作和当前任务对照，话题只能靠猜。
- **路径**：仓库根起写，指向整份文档；要定位到某一节时在括号里写节名，不用 `#锚点`。
- **放在离代码最近的地方**：函数 / 常量上方的注释 > 文件头注释 > rule > CLAUDE.md。越近，触发条件越具体，误读、漏读都越少；`pointer-guard` hook 也只认注释里的指针。
- 一份文档可以被几处指到，每处按自己的位置写重点和触发条件。指针只是登记，不算"一件事写两处"。
- 不留 `// 见文档`、`原因见 X` 这种没有重点、也没有触发条件的指针。

## 项目文档

### 位置与命名

- 路径：`<作用域>/.context/<领域>/<slug>.md`。涉及两个及以上领域、或说不清属于哪块的，放 `.context/` 顶层。
- **领域**指"讲的是系统哪一块"（`api`、`db`、`styling`），取自项目已有叫法：优先用同作用域 `.claude/rules/<领域>/` 已在用的名字，其次用代码里的模块名、目录名，不自造。rules 和 `.context/` 共用同一套领域名。**第一份文档就放进领域目录**，只分一层，不嵌套。
- **不按信息类型分目录**（不建 `decisions/`、`data/`、`pitfalls/`）：要改支付模块时，想看的是支付相关的一切，不管它是原因、数字还是坑。
- `.context/README.md`（只认作用域 `.context/` 顶层这一个）是文档入口，不是文档，见「入口」。
- 文件名 `<slug>.md`：英文小写短横线，概括主题（`retry-policy`，不是 `fix-bug`）。**不带日期、不带编号**：文档描述现状、原地更新，创建日期没有意义；两个分支为同一主题各建一份时，同名文件会在合并时冲突，正好把重复暴露出来。

### 入口

文档不会自动加载，每份都要被至少一处指到，否则基本不会被读到。按文档是从哪里拆出来的、能不能挂到代码上选：

| 文档 | 入口 | 什么时候被看到 |
|---|---|---|
| 从某处拆出来的扩展内容 | 原处的指针：代码注释、rule 或 CLAUDE.md 里那一行 | 读到那段代码 / 碰到那条 rule 的 `paths` / 一直 |
| 能挂到代码上、但不属于某一处的（外部系统调研、领域内几处共用的数据） | 领域索引 rule `<作用域>/.claude/rules/<领域>/context-index.md` | 碰到这个领域的代码时 |
| 挂不到代码上（评估过但没做的需求、外部系统限制、还没有代码的决定） | 文档入口 `<作用域>/.context/README.md`，由根 CLAUDE.md 常驻一行指过去 | 做新需求、评估方案前 |
| 两个时候都要看到的（见下文「两边都登记」） | 代码那一侧的入口（指针或领域索引）和 `.context/README.md` 都登记 | 两者 |

领域索引 rule 和文档入口的正文都是每份文档一行：**仓库根起的路径** + 一句"什么时候该读"（模板见 templates.md）。不要把文档内容抄进入口。

**从某处拆出来的文档**：原处的指针已经保证碰到相关代码时能看到，不用再进领域索引；只有希望碰到整个领域的代码时都看到，才另外登记进索引。

**领域索引 rule**：每个有不属于某一处的文档的领域一个，`paths` 覆盖这个领域的代码。碰到该领域的代码时，文档清单随 rule 自动进 context，成本只有几行；文档正文仍按需读。顶层的跨领域文档，登记进每个相关领域的索引。

**文档入口**：每个有这类文档的作用域一个 `.context/README.md`。它是挂不上 `paths` 的知识唯一的触发点，所以根 CLAUDE.md 的「更多上下文」里必须有一行，写明所有作用域的 `.context/README.md` 路径（包级 CLAUDE.md 碰到包里的文件才加载，等不到"提需求"的时候）。

**两边都登记**：一份文档在"改代码时"和"评估新需求时"都要被看到，就同时登记进代码那一侧（原处的指针或领域索引 rule）和 `.context/README.md`，两行各写各的"什么时候该读"。登记行只是指针，不算"一件事写两处"。典型的有：

- 挂得到代码上、但评估需求时也要考虑的：安装包体积、性能预算、外部系统的配额和限流——"做这个功能会不会超"在动代码之前就要知道
- 挂不到代码上、但和某个领域的代码也有关系的：某模块评估过但没做的功能，改那个模块时也值得看一眼

只在改代码时才用得上的文档不进 `.context/README.md`：它是每次做新需求都要过一遍的清单，越短越好。

新建、改名、删除文档时同步改入口。

### 内容

- **按主题组织，不按需求组织。**"这次做了什么"由 commit 记录，不要每做一个需求就落一个文档。一个主题一份，优先改已有的同主题文档。
- 第一行是标题，说清讲的是什么。没有固定模板，怎么分节按内容定。
- **写的是现状。** 情况变了就原地改写，不追加"更新：……"，不另建新文件再把旧的标成作废。改代码让指针里的重点（比如当前值）或文档里的说法不再成立时，在同一次改动里把两处都改掉，不等下次体检。旧说法交给 git；以后还用得上的历史留在正文里：
  - 被放弃的方案只在"怕以后有人重新提"时才留，一两句话写明放弃了什么、为什么。
  - 评估过但没做的需求：写明卡在哪（哪个外部系统、什么限制）、评估的时间，以及什么条件变了值得重新评估。
  - **实测数字**：每个都带测出它的日期和测法；迁移来的原文没写就标 `未记录`，不编造。同一指标测出新值时追加一行（表格见模板），不覆盖旧值；被测的东西已经没了才删。
- 文档只写背景。能挂到代码上的"做什么"写在原处（注释或 rule），原处留指针指向文档。

### 移动、改名、删除

会让指向它的入口（领域索引 rule、`.context/README.md`）、rule、代码注释里的指针、CLAUDE.md 失效。先在**整个仓库** grep 旧路径找出所有指针，一并改掉；整份删掉的把指针行一起删。有指针落在本次不可写的文件里，就不动这份文档，只提建议。移动和改名只在 organize-context 里做，record-context 不挪已有文件。

## 硬约束

- **禁止 `@` import**，指路一律用自然语言写**仓库根起的路径**（方便 grep 和脚本校验）。
- **`paths` 要窄到能真正起过滤作用。** 不许写 `**/*`、`src/**`、`src/*`、`packages/**` 这种一碰作用域就全中的；领域级的 `src/api/**` 可以。glob 相对 rule 所属作用域的根写（包内 rule 相对包目录，根 rule 从仓库根写完整路径），必须至少匹配到一个现存文件。例外：指向生成物或被 `.gitignore` 忽略的文件时，核对 glob 与生成脚本的输出路径一致即可。
- **rule 的 frontmatter `---` 必须是文件第一行**，否则 `paths` 不生效，rule 变成常驻。
- **CLAUDE.md 一条一行，不带原因。** 能用 `paths` 限定触发条件的一律走 rule 或注释；带"因为/当初/以前"的先拆开，原因再走一遍阶梯。确有扩展内容的，同一行末尾留指针（"改 X 前读 …"）。
- **单个文件的内容写注释，不写 rule。** `paths` 只匹配一个文件的 rule，只在那个文件没法写注释时才用。
- **rule 正文"做什么"在前，一两句原因跟在后面。** 正文不超过 10 行（不算 frontmatter 和空行），超出时按「扩展内容与指针」拆，正文留指针。
- **一件事只写一处。** 同一件事散在两个文件里比记在一个长文件里更糟。
- **新建前先查重。** 新建 rule、skill、文档前，按 slug 和主题关键词 grep **整个仓库所有作用域**的 `.claude/`、`.context/`、CLAUDE.md。有同主题的就改那份，不新建；它在别的作用域、而这次内容让归属变了的，照样改那份，挪动交给 organize-context。
- **代码注释守本分**：只收"读这段代码的人此刻需要知道的"，1–3 行：做什么、坑、一句原因，紧贴相关代码。经过、试过的方案、数字、长篇原因进文档，注释里留指针（见「扩展内容与指针」）。讲"这段代码在做什么、怎么用"的注释不受限制。
- **不碰用户级配置**：不改 `~/.claude/CLAUDE.md`、`~/.claude/settings.json`。

## hook

插件带两个 hook，都可以用环境变量关掉：

- **comment-hook**（PostToolUse，`CONTEXT_KEEPER_COMMENT_HOOK=0` 关闭）：Claude 新写了 4 行以上（超过注释的 3 行上限）的独立注释块时提醒它：注释只留必须知道的那一句，扩展内容进文档、原处留指针。只提醒，不阻断。
- **pointer-guard**（PreToolUse，`CONTEXT_KEEPER_POINTER_HOOK=0` 关闭）：Claude 要改的代码附近有指向 `.context/` 文档的注释指针、而本会话还没读过那份文档时，拦下这次编辑，把指针原文给它看，让它按触发条件决定先读文档还是直接重试，并提醒它改完后同步过时的重点和文档。同一会话里每处指针只拦一次（同一份文档被几处指到的，各拦各的），文档读过之后指向它的指针都不再拦。读过指 Read 成功，或 Bash 里用 cat / head / tail 这类命令读过；读失败、`git add` 这类只是提到路径的不算。主会话压缩上下文后，拦过、读过都重新算。和拦下它的那次编辑在同一条消息里的后几个 Edit 继续拦：它们是挨个执行的，提交时 Claude 还没看到拦截消息；Claude 看到消息后重新提交的那次放行（查不到消息 id 时退回按时间算，拦下后 3 秒内继续拦）。主会话和每个子代理各算各的，主会话读过、被拦过，子代理第一次改到时照样拦。"附近"指：改动范围内、外层函数 / 类的声明行、紧贴在它们上方的注释和紧跟在下面的 docstring，以及文件头注释。行注释、块注释（含 JSX 的 `{/* */}`）、Python docstring 里的指针都认；写在字符串或行尾注释里的不保证拦得到。文件头注释指文件开头、后面是空行或 import 的那几段（开头的 shebang、PHP 的 `<?php`、`'use client'` 这类指令、Vue / Svelte 的 `<script>` 标签不算代码，跳过）；紧贴着第一个声明的注释算那个声明的，所以涉及整个文件的指针写在文件头时，和下面的代码之间空一行。只认非 Markdown 文件里的指针，rule 和 CLAUDE.md 里的不管。指针按项目根起的路径解析：项目根取离文件最近的 `.git`，不是 git 仓库时取启动会话的目录。

## 检查脚本

能确定性校验的部分交给脚本，不要再手工逐条核对：

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/check.mjs" [路径] [--comments]
```

检查：rule 的 frontmatter 位置、缺 `paths`、glob 匹配不到文件 / 基准错位 / 过宽、正文超过 10 行、只匹配一个能写注释的文件（认得出是生成物或 lockfile 的不报）；skill 缺 description；CLAUDE.md 和 rule 里的 `@` import；CLAUDE.md 疑似带原因的行；文档文件名（日期/编号前缀、非 slug）、嵌套领域目录、缺领域索引 rule（已被 rule、CLAUDE.md 或代码注释指到的文档不算）；`.context/README.md` 没被根 CLAUDE.md 指到；失效指针（只查 CLAUDE.md、rule、skill、`.context/` 文档和源码里的注释，代码块里的示例不算；源码字符串里、脚本不认得的非 Markdown 文件里指得到文档的路径算已登记，指不到的不报）；没写"什么时候读"的指针；孤儿文档（没登记在任何入口、rule、CLAUDE.md 或代码里）；`.context/`、`.claude/rules/`、`.claude/skills/` 被 `.gitignore` 忽略；放在 `.claude/` 下或按类型分目录的文档。`.context/` 是否已被别的用途占用查不出来，要人工看。`--comments` 额外列出长注释块（4 行以上）和带信号词的注释作为搬运候选，3 行以内、已经带着有效指针的注释不列。带路径时只报告该路径下文件的问题；路径相对当前目录找不到时，按仓库根起的路径再找一次。

脚本的判断是机械的：「警告」「提示」要结合上下文看（比如 glob 指向的生成物、确实该常驻的 rule），「错误」基本都要处理。有错误时退出码为 1。`node` 不可用时按本规范手工检查。脚本没有依赖，用户想接进 CI 时把 `check.mjs` 连同 `lib/` 目录一起复制进项目。

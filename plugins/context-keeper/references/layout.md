# context-keeper 规范

`organize-context` 和 `record-context` 共用这份规范。

目标：**只记 Claude 不知道就会做错的事，写在它用得上时一定会看到的地方，越短越好。**

- 只和一个文件（或其中一段代码）有关的，写成**代码注释**，紧贴相关代码；
- 几个文件共用的，写成带 `paths` 的 **rule**；
- 有步骤的流程，写成 **skill**；
- 任何任务都可能违反的硬约束，才进 **CLAUDE.md**。

除此之外没有别的去处。经过、历史、实测流水、被否掉方案的论证都不进仓库文件：它们照常写在 commit message 和 PR 描述里，本规范不管，也不在代码里留指向它们的指针。想知道某段代码当初为什么这样写，`git blame` / `git log -L` 从那几行就能找到对应的提交和 PR。

## 加载机制（2026-09 已核实，直接按此执行；实际观察与某条矛盾时以观察为准，并在计划或报告里指出）

1. `.claude/rules/` 下的 `.md`（递归发现，可用子目录组织）带 `paths:` glob → 只有读/改到匹配文件时才进 context。没有 `paths` 的 rule 常驻，`paths` 只有 `"**"` 的也常驻。`paths` 可以是列表或逗号分隔的字符串，支持花括号（`*.{ts,tsx}`），按 **gitignore 语义**匹配：不含 `/` 的模式（`*.test.ts`）匹配任意深度；含 `/` 的相对作用域根锚定；匹配到目录就等于匹配目录下所有文件，所以 `src/api`、`src/api/**` 等价，`src/*` 等于整个 `src/`；`./` 开头的匹配不到任何文件（2026-11 读 Claude Code 2.1.319 源码核实）。
2. 子目录里的 `CLAUDE.md` → 碰到那个目录的文件时才加载，但**一旦触发是整文件加载**，也不支持 `paths:`。同目录的 `CLAUDE.local.md` 加载时机相同（2026-11 实测：子目录里的也按需加载），但它只在本机这份 checkout 里，要靠 `.gitignore` 挡在仓库外。
3. Skill → 启动时只加载 description，正文和它目录下的其他文件在用到时才读。子包的 `.claude/skills/` 也有效，碰到该包的文件后才可用，重名时用 `apps/web:deploy` 这种目录限定名。
4. 子包的 `.claude/rules/` 同样有效，**`paths` 相对该子包解析**（官方文档没写，已实测）。
5. **`@path` import 是 eager 的**，启动就展开进 context，完全不省 token。**禁止**用它来"拆分"。
6. 自动记忆在 `~/.claude/projects/<project>/memory/`，不在仓库里，只对当前用户、当前机器生效；`MEMORY.md` 前 200 行常驻。

由此得出几点：

- **根 CLAUDE.md 和目录级 CLAUDE.md 都要瘦**。根的常驻；目录级的触发即全量——一个 400 行的包级 CLAUDE.md，碰了包里任意一个文件就全进来。
- **只匹配一个文件的 rule，和写在那个文件里的注释成本一样**：碰到文件就整条加载，Claude 只读文件的一部分时也一样。它比注释差在离代码远、定位不到函数，所以单个文件的内容写成注释；rule 留给几个文件共用的内容，以及没法写注释的文件（见「去处」）。
- **写在原处的内容一定被看到，另放一处、靠指针按需读的内容常常被漏读**，而且要维护指针。所以必须知道的结论就写在原处，写不下就说明写得太多了，不拆到别处。

## 记录的单位：一条结论

仓库里记下的每一条，都是一条面向以后的**结论**：

- 做 X：「改 schema 后必须跑 `pnpm db:generate`」
- 别做 Y：「别在网关前加熔断：和网关限流叠加后会长时间不可用」
- 改 A 要同步 B：「改这里的 token 后跑 `pnpm tokens:build`，生成物不会自动更新」
- 外部系统的特性，写成「症状 → 原因 → 怎么办」：「这个站把 429 当业务报错返回（余额或分组问题），不是限流，别按限流退避重试」
- 遇到 X 类决策时先 / 按 Y：「定价和套餐的取舍，先看主要竞品怎么做」

**理由最多一句**，而且只在两种情况下写：它能让人判断这条结论什么时候不再成立（「重试上限 3：网关连续 5 次失败会封 IP」，网关的规则一变，上限就该跟着变），或者能防止下一个 Claude 把它当成多余的东西"优化"掉。去掉理由照样会照做的，删掉理由。

历史决策、实测数据、被否掉的方案都**不是**独立的记录类别。它们只以两种身份出现：本身就是结论（被否掉的方案写成「别做 Y」），或者是结论那一句理由里的一个事实（「连续 5 次失败封 IP」里的 5）。下面这些都不写：

- 经过和时间线：「某天发现 → 某天改 → 后来又改回」、「以前是 5 次，出过一次事故」
- 状态：「已上线」「尚未部署」「待办」「目前还在观察」。状态一过时就会误导人，而且没有谁会回来改它
- 实测流水：测了几次、每次的数字、带日期的表格
- 被否掉方案的完整论证、推导过程
- 「这次改了什么、改了哪些文件」

判断办法是看**形式**，不是看长短：这句话是在告诉下一个 Claude **怎么做**，还是在讲**发生过什么**？只讲发生过什么的，再短也不写。

**日期**只有一种用法：给外部系统的事实标上观测时间（「2026-11 实测：…」）。外部站点、第三方 API 随时会变，日期告诉读的人这条还有多可信，碰到对不上的就该重测。这是一个现在时的事实加上它的确认时间，不是一段经过。

## 准入门槛

写进仓库的每一行都有成本：常驻的占 context，过时了会误导，而且以后每次改动都可能要维护它。所以先问「值不值得留」，再问「放在哪」。一条结论同时满足下面四条才记：

1. **有具体的错**：写得出一句「不知道这条，Claude 会做 X，结果是 Y」。X 不只是写错代码，也可以是一个判断或建议：偏离用户定下的方向、漏看该参考的对象，这类错同样不报错。写不出具体动作的（「了解背景有帮助」「以后可能用得上」）不记。
2. **读仓库推不出来，或者重新弄清代价高**：读那几行代码、配置、测试就能知道的，不记，下一个 Claude 也会读到。典型的推不出来的有：业务和政策上的约定、仓库设置（比如开着 squash 合并）、外部系统的行为（只有实测才知道，重测要花钱、花时间，还可能误判）。
3. **拦不住**：类型检查、测试、lint、CI、构建失败、运行时报错都拦不下。拦得住的不记；本该拦住却没拦住的，标 `HOOK`。
4. **静默或代价高**：错了不报错（数据静默丢失、页面静默不显示、口径静默混算），或者代价高、难回滚（线上事故、账单、数据损坏、对外发布）。会立刻报错、一分钟就能改回来的，不记。

满足这四条的，常见的来源是：

- **被纠正过**：本次会话里用户纠正了 Claude 的做法（「不对，这里要用 merge commit」），或者真实环境出了错（部署失败、线上数据不对、外部站点的行为和代码的假设不一样）。这是最可靠的信号：说明按常理推会推错。
- **外部系统的实测结果**：站点的怪癖、第三方接口要带的特殊参数、配额和限流。写在那个站点或接口的配置旁边，带上观测日期。
- **还没错过、但错了不可逆**：删生产数据、花钱的调用、对外发布。等错了再记就晚了。
- **用户给出的业务方向或决策依据**：参考谁（主要参考的竞品）、面向谁（目标用户群）、什么优先、什么不做。读代码推不出来，而且只有用户说了算：用户在这里的特殊地位来自业务方向归用户定，不是用户可以绕过门槛。所以它照样要写成「遇到 X 类决策时，先 / 按 Y」；写不成的（产品介绍、历史沿革、公司背景、单独一句「目标用户是 Z」却说不出会影响哪类决策）不记。X 取自用户的话或当前正在做的那个决策，Claude 不替用户补；补不出来时回复「不记」并问一句它影响哪类决策。用户让记的经过、状态（「记一下这次怎么修的」）不属于这一类，照常过门槛。

反过来，**Claude 自己读代码、跑命令查出来的**，下一个 Claude 也查得出来，最多慢一点：不记。

**拿不准时不记。** 漏记一条，代价是某次多查几分钟、或者被用户再纠正一次（那时它就过了门槛）；多记一条，代价是永久的。删掉的东西在 git 历史里随时找得回来。

几个例子：

- 记：「新增错误类型时，`apps/web` 必须先上线认识它，生产方才能开始写」。顺序反了，统计会静默算错，类型和测试都拦不住。
- 记：「pnpm 给脚本传参不要写 `--`」。后面的参数会被静默吃掉，然后跑一遍全量任务。
- 记：「Worker 上限 10 MB（gzip 后）」。超了部署会报错，但等到部署失败才发现，功能可能已经白做了；写在 `wrangler` 配置旁边或包级 CLAUDE.md 里，评估要不要引入一个依赖时就能看到。
- 记：在某个站点的配置条目旁边写「2026-09 实测：不带 `reasoning_effort: 'none'` 会 400」。读代码推不出来，重测要花钱。
- 记：订阅相关包的 CLAUDE.md 里写「定价和套餐的取舍，先看主要竞品怎么做」。不知道这条，Claude 给的建议会自说自话，不报错，也没有测试拦得住。
- 不记：网关切换的排障记录，「周一发现 → 周二改 → 当天又改回」。现在用哪个、为什么，代码里就有；经过留在 commit 和 PR 里。
- 不记：某次探测的 TTFT 表、令牌状态、上线进度。都是那一刻的状态，过几天就不成立了。
- 不记：支付回调超时取 5 秒，注释里已经写了「上游最慢 3 秒，留余量」。再多写都是重复。

## 去处

| 标签 | 判据 | 去处 |
|---|---|---|
| `ALWAYS` | 任何任务都可能违反的硬约束（commit 规则、语言/风格约定、绝对禁止做的事）；约束整个包、或还没有代码可挂的业务方向（见判据阶梯第 5、6 步） | 全仓通用 → 根 `CLAUDE.md`；只在某包 / 某个已有目录级 CLAUDE.md 所在目录内成立、且其中任何任务都适用 → 那个 CLAUDE.md。一条一行 |
| `HOOK` | 能被脚本/lint/CI 确定性校验、但现在还没被拦住的 | 建议改成 hook、lint 或测试。**只提建议，不自己改 CI**。检查落地前文字不删，继续按阶梯归类放好；落地后由用户删，或 organize-context 体检时列出来 |
| `COMMENT` | 只和**一个文件**（或其中一个函数、一段代码、一个配置条目）有关、且这个文件能写注释的 | 代码注释，紧贴相关代码：函数 / 常量 / 配置条目上方，涉及整个文件的写在文件头。1–3 行 |
| `PATH-RULE` | 只在碰到特定文件时才需要知道、但**涉及多个文件**的：一类文件的约定、一个目录的坑、"改 A 必须同步 B"；以及只涉及一个文件、但这个文件**没法写注释**的（JSON、lockfile、生成物、二进制资源，或写了会被工具覆盖） | `<作用域>/.claude/rules/<领域>/<name>.md`。正文不超过 10 行 |
| `SKILL` | 有步骤的流程（发布、迁移、加一个新的外部站点），平时不需要 | `<作用域>/.claude/skills/<name>/SKILL.md`。流程要用的参考资料（各类站点的接入差异、字段对照）可以放在 skill 目录下的其他文件里，用到时才读；它们同样只写结论，不写经过 |
| `DERIVABLE` | 没过「准入门槛」的：读代码就能知道的、只是复述某次改动的，以及经过、状态、流水、推导、没人用的数字 | **删除** |
| `STALE` | 已不成立、与现状矛盾、或引用了不存在的文件 | **删除**，单独列出让用户确认 |
| `PERSONAL` | 个人偏好、个人工作习惯 | 不进仓库，留在自动记忆。想对所有项目生效时，给出可粘贴到 `~/.claude/CLAUDE.md` 的文本，**不直接改那个文件** |
| `ENV-BOUND` | 换台电脑、网络、操作系统就不成立的：本机路径、本机版本、端口占用、代理/网络、只在某台机器出现的怪现象、凭据 | 不进仓库，留在自动记忆 |

有条件成立的（"在 macOS 上 X 会失败"、"Node 20 以下会报 Y"）不算 `ENV-BOUND`：换台同类环境照样遇到。按上表正常归类，**第一句写明适用条件**（如"仅 macOS："）。

**敏感信息一律不进仓库**，不论原本是什么标签：API key / token / 密码 / 私有仓库地址 / 内网 IP 或域名 / 含用户名的绝对路径 / 任何用户没打算公开的信息。向用户报告时只说类型和位置，不打出值本身。

**业务方向和决策依据公不公开，由用户定**：点名的竞品、目标用户、什么不做，写进公开仓库就等于对外说了。写之前先问一句（用户已经说了放哪的不问）：
- 进仓库 → 按判据阶梯放。
- 只留本机 → 写一行进 `CLAUDE.local.md`，放在它约束的那片代码最近的目录里（子目录里的按需加载，见加载机制第 2 条）：只约束定价模块的放那个模块的目录，约束整个包的放包目录，跨几片目录的放它们最近的共同上级，还没有代码可挂的放仓库根。本地没有 `paths` 那样的收窄写法（`.claude/rules/` 被忽略时检查脚本会报错），放到仓库根的会常驻加载。
- 问的时候说清代价：队友、别的 worktree、别的机器都看不到。
- 写之前确认它进不了仓库：不是 git 仓库的直接写；`git ls-files <路径>` 有输出说明已经提交过，停下来告诉用户先 `git rm --cached`（`git check-ignore` 不报已跟踪的文件，所以这一步要先做）；`git check-ignore -q <路径>` 退出码是 1 就是没被忽略，停下来告诉用户在 `.gitignore` 里加一行 `CLAUDE.local.md`。

**挂不到代码上、又不是硬约束的**（评估过但没做的需求、以后可能要做的功能）不记。真是「别做 X」这种约束的，它就是 `ALWAYS`，写进 CLAUDE.md 一行；否则哪天有人重新提出来，用户会纠正，那时它才过了门槛。用户定下的业务方向不算在这里：还没有代码的，先写一行进根 CLAUDE.md，代码出现后挪到它约束的那片代码上（见判据阶梯第 5、6 步）。

**写不下的**：注释超过 3 行、rule 超过 10 行时，不要把多出来的部分挪到别处，先删：经过、状态、数字表、被重复的话。删完还写不下，通常是几件事混在了一起：

- 是几个文件各自的知识 → 按「谁需要知道」拆成几处注释或几条窄 rule
- 是一个流程 → `SKILL`
- 是一个每次都要重新做的测量或核对 → 写成脚本或测试（`HOOK`），文字只留「改 X 前跑 Y」

## 判据阶梯

按顺序问，第一个"是"就停。

0. 它属于这个项目吗？个人偏好 → `PERSONAL`；换台机器就不成立 → `ENV-BOUND`
1. 它是一条结论吗？只讲发生过什么的（经过、状态、流水）→ `DERIVABLE`，删除。混着结论和经过的，只留结论和最多一句理由，往下走
2. 过「准入门槛」了吗？没过 → `DERIVABLE`，删除。commit 或 PR 里写没写过不影响判断：过了门槛的照样写进仓库（Claude 平时不翻 git 历史），没过的不写
3. 能写成脚本自动校验吗？能 → 同时打上 `HOOK`，但**不停**，继续往下问，定出检查落地前文字放哪
4. 有步骤、平时用不上吗？是 → `SKILL`
5. 只在碰到特定文件、目录或文件类型时才需要知道吗？是 →
   - 适用于某个已有目录级 CLAUDE.md 所在目录内任何任务 → `ALWAYS`，放进那个 CLAUDE.md
   - 适用于某个包内任何任务（monorepo）→ `ALWAYS`，放进那个包的 CLAUDE.md（没有就新建），不写成覆盖整个包的宽 rule
   - 只涉及一个文件、且这个文件能写注释 → `COMMENT`，写在相关的函数、常量、配置条目上方；涉及整个文件的写在文件头
   - 否则（涉及多个文件，或文件没法写注释）→ `PATH-RULE`

   "涉及几个文件"按**谁需要知道**算，不按这条知识讲的是哪个文件算。约束的是调用方的（"必须在 X 之后调用""返回值不能缓存"），需要知道的是调用它的那些文件：调用方分散的，写进定义处的 API 文档注释（JSDoc / docstring，查定义、IDE 悬停时看得到）；调用方集中在某个目录的，写成 `paths` 覆盖调用方的 `PATH-RULE`。

   一类实体（外部站点、供应商、第三方接口）各自的特性，写在**那个实体自己的配置条目**旁边，不攒成一条覆盖所有实体的 rule：碰到哪个站，Claude 一定会读它的配置。

   业务方向或决策依据挂在它约束的那片代码上，按它约束的范围定，不按它在 monorepo 还是单仓库里定：约束的是一个包（或某个已有目录级 CLAUDE.md 所在目录）的整体，那里任何任务都可能用上 → `ALWAYS`，那个 CLAUDE.md 一行；只约束包里或仓库里的几片代码（定价、订阅模块），不论跨不跨包 → `PATH-RULE`，`paths` 只覆盖那几片，不写整个包。它约束的是决策，不落到某个函数上，不写成注释。还没有任何代码可挂的，见第 6 步。

   这一步要严格：能挂到代码上的都挂上，能挂到一个文件上的不写成 rule。
6. 剩下的是任何任务都可能违反的硬约束，或还没有任何代码可挂的业务方向 → `ALWAYS`，写进根 CLAUDE.md。后者在代码出现后按第 5 步挪走
7. 都不是 → 不记

## 仓库形态与作用域

### 判断形态

命中下列任一信号即为 **monorepo**，否则为**单仓库**：

- `pnpm-workspace.yaml`、根 `package.json` 的 `workspaces`、`lerna.json`、`nx.json`、`turbo.json`、`rush.json`
- `Cargo.toml` 的 `[workspace]`、`go.work`、`settings.gradle(.kts)` 的 `include`、`pom.xml` 的 `<modules>`
- 以上都没有，但有多个带独立清单文件且各自构建的目录——拿不准，说明依据，让用户确认

**包**是 workspace 配置实际匹配到的成员目录，以配置为准，不凭目录名猜。

### 作用域

**作用域**是一套 `CLAUDE.md` + `.claude/` 的挂载点：单仓库只有仓库根一个；monorepo 是仓库根加每个包。包的 `.claude/` 只在真有内容时才建。

- 内容涉及的文件全在某个包内 → 该包；涉及两个及以上包 → 根；单仓库 → 一律根。
- `.claude/` 只放 Claude Code 要从这里加载的东西。本规范往里写的只有 `rules/`、`skills/`；已有的 `settings*.json`、`commands/`、`agents/`、hook 脚本等原样保留。
- 根 CLAUDE.md 可以是 `CLAUDE.md` 或 `.claude/CLAUDE.md`，两者等价；两个都存在时交给用户决定是否合并。
- `.claude/` 是点开头的目录，有些工具默认跳过它：Grep / Glob 时显式传 `.claude/` 作为 path。
- `.claude/rules/`、`.claude/skills/` 必须进 git。不少项目把 `.claude/` 整个忽略，或只放行 `settings.json`：这时写进去的 rule、skill 只在本机生效，队友看不到。新建前用 `git check-ignore` 确认，被忽略就交给用户调整 `.gitignore`（通常只需要忽略 `settings.local.json`）。

**领域**（rule 的子目录名 `<领域>`）指"讲的是系统哪一块"（`api`、`db`、`styling`），取项目已有叫法：先看同作用域 `.claude/rules/` 下已有的领域目录名，其次用代码里的模块名、目录名，不自造。rule 文件名用英文小写短横线概括主题（`retry-policy`），不带日期、不带编号。

### 目录级 CLAUDE.md

单仓库的子目录（如 `src/server/CLAUDE.md`）或包内更深层的 CLAUDE.md，按包级同样的标准瘦身：只留"该目录内任何任务都适用"的。**不要**在这些目录下另建 `.claude/`，拆出来的东西放进所属作用域。**不要**为了放某条规则新建目录级 CLAUDE.md，没有的走 rule。

## 硬约束

- **禁止 `@` import**，提到文件一律用自然语言写**仓库根起的路径**。
- **不写指针。** 不写「详见 X」「原因见 PR #123」「改 X 前读某文档」：结论就写在原处，经过在 git 里，`git blame` 找得到。指向 skill 的「做 X 时用 `/deploy`」不算指针，照常写。
- **`paths` 要窄到能真正起过滤作用。** 不许写 `**/*`、`src/**`、`src/*`、`packages/**` 这种一碰作用域就全中的；领域级的 `src/api/**` 可以。glob 相对 rule 所属作用域的根写（包内 rule 相对包目录，根 rule 从仓库根写完整路径），必须至少匹配到一个现存文件。例外：指向生成物或被 `.gitignore` 忽略的文件时，核对 glob 与生成脚本的输出路径一致即可。
- **rule 的 frontmatter `---` 必须是文件第一行**，否则 `paths` 不生效，rule 变成常驻。
- **CLAUDE.md 一条一行，不带原因。** 能用 `paths` 限定触发条件的一律走 rule 或注释；带"因为/当初/以前"的先拆开，原因过不了门槛就删。
- **单个文件的内容写注释，不写 rule。** `paths` 只匹配一个文件的 rule，只在那个文件没法写注释时才用。
- **rule 正文"做什么"在前，最多一句理由跟在后面**，不超过 10 行（不算 frontmatter 和空行）。一条 rule 的 `paths` 超过 10 项，多半是把几组「改 A 同步 B」攒成了一张表，按「谁需要知道」拆窄。
- **少用强调。** 一条 rule 里 ⚠️ 和加粗最多两处，处处都强调等于哪处都不突出。
- **一件事只写一处。** 同一件事散在两个文件里比记在一个长文件里更糟。
- **新建前先查重。** 新建 rule、skill 前，按主题关键词 grep **整个仓库所有作用域**的 `.claude/`、CLAUDE.md，以及相关代码的注释。有同主题的就改那份，不新建；它在别的作用域、而这次内容让归属变了的，照样改那份，挪动交给 organize-context。
- **改动让已记下的结论不再成立时，同一次改动里改掉或删掉。** 现在拦得住了（加了测试、lint、类型）的直接删。
- **代码注释守本分**：只收"读这段代码的人此刻需要知道的"，1–3 行：做什么、坑、最多一句理由，紧贴相关代码。讲"这段代码在做什么、怎么用"的注释不受限制，不归本规范管。
- **不碰用户级配置**：不改 `~/.claude/CLAUDE.md`、`~/.claude/settings.json`。

## 旧版的项目文档

0.9.x 及更早的插件会建项目文档目录 `context-docs/`（更早叫 `.context/`），在注释、rule、CLAUDE.md 里留「重点 + 什么时候读 + 路径」的指针，并用领域索引 rule（`.claude/rules/<领域>/context-index.md`）和文档入口（`context-docs/README.md`）登记文档。0.10.0 起不再有这些东西，整理时按下面处理（具体步骤见 organize-context）：

- **指针**：原处的「重点」就是结论，留下；「什么时候读 + 路径」删掉。重点本身是经过或状态的（「2026-10 起改成 X」「尚未部署」），按准入门槛重过，改写成结论或删掉。指到的文档已经不在了的指针同样处理。
- **文档**：每份读一遍，找出其中过得了门槛、而原处的重点里还没有的结论，按判据阶梯放到原处或别处；其余（经过、状态、实测流水、表格）不迁移。然后删掉文档。文档全文留在 git 历史里，`git log --all -- <文档路径>` 找得回来。被代码字符串（日志、报错提示、测试数据）提到的文档，删之前先由用户改掉那些字符串：改它们要动可执行代码。
- **领域索引 rule**：每一行的重点按判据阶梯重过一遍，过了门槛的放到该放的地方（多半是一条窄 rule 或某处注释），然后删掉索引 rule。
- **文档入口、根 CLAUDE.md 里指向它的那一行，以及指向整个文档目录的行**（「本包的历史决策在 …」）：入口里的重点同上处理，然后一起删掉。
- **按类型分目录的旧文档**（`context/decisions/`、`decisions/`、`adr/` 这类）和放在 `.claude/` 下的文档：更早的插件版本往这两种地方放过文档。有「重点 + 路径」的指针指向它、确认没有被代码读取的，同文档；团队自己维护的 ADR、别的工具放的文件不归本规范管，不动。

## hook

插件带一个 hook，可以用环境变量关掉：

- **comment-hook**（PostToolUse，`CONTEXT_KEEPER_COMMENT_HOOK=0` 关闭）：Claude 新写了 4 行以上（超过注释的 3 行上限）的独立注释块时提醒它：注释只留一条结论和最多一句理由；经过、状态、数字表直接删，留给 commit 和 PR。只提醒，不阻断。

## 检查脚本

能确定性校验的部分交给脚本，不要再手工逐条核对：

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/check.mjs" [路径] [--comments]
```

检查：rule 的 frontmatter 位置、缺 `paths`、glob 匹配不到文件 / 基准错位 / 过宽、正文超过 10 行（没有 `paths`、常驻加载的 rule 也查）、只匹配一个能写注释的文件（认得出是生成物或 lockfile 的不报）；skill 缺 description；CLAUDE.md 和 rule 里的 `@` import；CLAUDE.md 疑似带原因的行（`CLAUDE.local.md` 不查，里面是只留本机的内容）；`CLAUDE.local.md` 没被 `.gitignore` 忽略或已经提交进仓库；`.claude/rules/`、`.claude/skills/` 被 `.gitignore` 忽略；旧版的项目文档目录（`context-docs/`、`.context/`），疑似按类型分的文档目录和放在 `.claude/` 下的文档（提示，是不是旧版文档由人确认）；CLAUDE.md、rule、skill、子代理和命令的定义、源码注释里指向旧版文档目录的指针（按文件汇总行号；源码按所在语言的注释语法认注释）；这些 Markdown 的代码块里提到旧版文档目录的行（提示）；仓库里还有旧版文档时，可执行的行（字符串、命令参数、配置值、ignore 规则）和别的 Markdown（README、对外文档）里提到它的行（提示）。`node_modules/`、`vendor/` 下的第三方文件不查。`--comments` 额外列出长注释块（4 行以上）和带信号词的注释作为整理候选，认得出是生成物的文件不扫。带路径时只报告该路径下文件的问题；路径相对当前目录找不到时，按仓库根起的路径再找一次；路径在别的 git 仓库里时，检查那个仓库；在当前仓库外面、又不在 git 仓库里时，把那个目录当作不是 git 仓库的项目查。

**修剪候选**另列一块，按「准入门槛」和「记录的单位」找可能该删的东西，不计入错误、警告的计数，也不影响退出码：

- 过宽的 rule：`paths` 超过 10 项（按逗号切开，花括号不展开）
- 强调泛滥（提示）：一条 rule 的正文里 ⚠ 和加粗加起来超过两处（常驻加载的 rule 也查）
- 叙述形态（提示）：CLAUDE.md、rule、skill 里带完整日期（`2026-09-25`）、状态词（「已上线」「尚未部署」「待办」）或叙述词（「以前」「曾经」「后来」「当时」「一度」「改回」）的行，按文件汇总。只标年月的观测日期（「2026-11 实测」）不算

输出开头有每个作用域的规模：rule 条数和正文行数（不算 frontmatter 和空行；没有 `paths`、常驻加载的 rule 也算在内）、skill 数、旧版文档数、指向旧版文档的指针行数。整理前后各跑一次，对比效果。

脚本的判断是机械的：「警告」「提示」要结合上下文看（比如 glob 指向的生成物、确实该常驻的 rule），「错误」基本都要处理。有错误时退出码为 1。`node` 不可用时按本规范手工检查。脚本没有依赖，用户想接进 CI 时把 `check.mjs` 连同 `lib/` 目录一起复制进项目。

# 整理项目上下文

开始前先完整读两份规范，后面所有标签、去处、模板都以它们为准：

- `${CLAUDE_PLUGIN_ROOT}/references/layout.md`：加载机制、作用域、标签、判据阶梯、扩展内容与指针、项目文档与入口、硬约束、hook、检查脚本
- `${CLAUDE_PLUGIN_ROOT}/references/templates.md`：rule / 领域索引 rule / 文档入口 / 文档 / skill / CLAUDE.md 索引模板

## 工作方式

**两阶段：先调研出计划，用户批准后再执行。批准之前不要创建、修改或删除任何文件。**

- 处于 plan mode：计划做完用 ExitPlanMode 提交。否则把计划作为回复输出，等用户明确同意。
- 计划一次性交出，中间不停下来问。拿不准的全部放进「需要拍板」。

## 范围

- 只处理本仓库内的文件，不读父目录和 `~/.claude/CLAUDE.md`。例外：阶段五的自动记忆目录，以及定位它要读的 settings（只读）。
- 带了参数（`$ARGUMENTS`）就只处理该路径下的 CLAUDE.md、代码注释、`.claude/`、`.context/`：
  - 参数是某个包：只写该包的作用域；根的 CLAUDE.md、`.claude/`、`.context/` 只读，用于查重，上移到根的候选只写成建议。
  - 参数是普通目录：拆出来的 rule / 文档写进所属作用域（允许），所属作用域的 CLAUDE.md 只读。
  - 阶段五只沉淀归属于参数范围的记忆条目，其余列一句"不在本次范围"，不动。

## 阶段一：跑检查脚本，判断形态和模式

1. 跑 `node "${CLAUDE_PLUGIN_ROOT}/scripts/check.mjs" "<路径>" --comments`。`<路径>` 是从参数里取出的那一个仓库内路径（参数夹着说明文字的只取路径；拿不准取哪个时不带路径跑，按最窄的合理理解定范围，把范围的歧义写进「需要拍板」，不中途停下来问），加引号传；没带参数就去掉 `"<路径>"`。脚本以退出码 2 报「路径不存在」「路径不在仓库内」时是路径传错了，改正后重跑，不要当成 `node` 不可用。脚本输出是后面几个阶段的输入：rule、文档、指针、`@` import 这些机械问题以它为准，不用再手工逐条核对。`node` 不可用时在计划里注明，按 layout.md 手工检查。
2. **形态**：按 layout.md「判断形态」定 monorepo 还是单仓库，列出所有包。拿不准写进「需要拍板」，先按单仓库处理。
3. **模式**，按作用域分别判断：
   - **迁移**：还没有这套结构（没有带 `paths` 的 rules、没有 `.context/`），CLAUDE.md 里混着各种内容。
   - **体检**：已经在用这套结构。
   - 根已整理、某个包还没动的，各走各的。

计划开头写明形态、包列表、每个作用域的模式。

## 阶段二：调研（两种模式都做）

1. 找出所有 `CLAUDE.md` / `CLAUDE.local.md`（含 `.claude/CLAUDE.md`），记录行数。`CLAUDE.local.md` 是个人文件，只提建议，不迁移进仓库文件。
2. 脚本报了 `.context/`、`.claude/rules/`、`.claude/skills/` 被 `.gitignore` 忽略的作用域，写进「需要拍板」，要写进去的条目标出来，用户解决前不执行。`.context/` 是否已被别的用途占用，脚本**查不出来**，要自己看：已有 `.context/` 的作用域，`ls` 一遍并 grep 代码和配置里对 `.context` 的引用，里面有不是 Markdown 文档、或被代码 / 工具读取的文件，同样写进「需要拍板」。
3. 把每个 CLAUDE.md、以及缺 `paths`（等于常驻）的已有 rule **逐条**拆开（一条 = 一个独立语义单元），按判据阶梯打标签，按归属定作用域；标为 `DOC` 的同时定领域和入口（领域索引 rule 还是 `.context/README.md`）。
4. 找**错位**和**重复**：
   - monorepo：2 个及以上包里语义重复的 → 上移到根的候选；根里只对某个包成立的 → 下沉候选；包里其实全仓通用的 → 上移候选。
   - 单仓库：目录级 CLAUDE.md 里全仓通用的 → 上移候选；根里只对某个目录成立的 → 下沉为 rule，那个目录已有目录级 CLAUDE.md 且这条适用其中任何任务时，下沉进那个 CLAUDE.md。
5. 根 CLAUDE.md 末尾的「更多上下文」索引缺失、缺"写入约定"那一行（或那一行是旧版插件写的、和模板不一致）、或「文档入口」那一行没列全所有作用域的 `.context/README.md`（见 templates.md）的，按模板补。

## 阶段三：代码注释

搬运候选来自脚本 `--comments` 的输出（长注释块 + 带信号词的注释）。`node` 不可用时，用 Grep 找连续 5 行以上的独立注释块和带"为什么 / 以前 / 注意 / 坑 / 性能 / benchmark / workaround"等词的注释。脚本是机械匹配，命中后逐段读原文判断：

- 讲**这段代码在做什么 / 怎么用** → 留着，别动
- 讲**改这里时必须注意什么**（"顺序不能换"、"这个值不能超过 3"），或**为什么当初这么选、以前是什么方案、实测数字** → 按 layout.md「扩展内容与指针」拆：必须知道的那一句留在原处（`COMMENT`），扩展内容拆成 `DOC`，原处留指针。整段 3 行以内就说完的不动
- 同样的内容在**几个文件**里重复出现 → 合成一条 `PATH-RULE`，各处注释删掉
- 只是复述**某次改动做了什么** → `DERIVABLE`，删掉，不留指针
- **流程**（"重新生成这个文件的步骤是……"） → `SKILL`

原处留下的指针按 layout.md「指针怎么写」：重点 + 什么时候读 + 路径。

**绝对不要动**：license header、JSDoc/TSDoc/docstring 等 API 文档注释、`eslint-disable` / `@ts-ignore` / `prettier-ignore` 等有实际功能的注释、类型标注注释、任何行尾注释。只处理独立成段的注释。

不要为了瘦身而瘦身：20 行注释讲的全是"这段代码在干嘛"，就该留着。拿不准的列进计划让用户决定。

## 阶段四：体检（体检模式的作用域）

脚本报出的每条「错误」「警告」都过一遍，确实是问题的写进计划（是生成物、确实该常驻等误报的，一句话说明）。脚本查不出、要读内容判断的，再逐项看：

1. **CLAUDE.md 回胀**：多行条目、段落、带原因的解释、能用 `paths` 限定的内容。
2. **一事多处**：同一件事出现在 CLAUDE.md、rule、文档、代码注释中的两处以上。
3. **注释、rule 与文档的分界**（按 layout.md「标签与去处」「扩展内容与指针」）：
   - **单文件 rule**（脚本报「只匹配一个文件」）：必须知道的那一句改写成那个文件里的注释，紧贴相关代码；扩展内容拆成文档，注释里留指针；删掉这条 rule。文件没法写注释的保留 rule。从 0.4.x 升级的项目会有不少这类 rule。
   - rule 正文超过 10 行、带实测数字的历史表格、同一背景几处重复 → 扩展内容拆成文档，rule 留"做什么"、一两句原因和指针。
   - **没写"什么时候读"的指针**（脚本报出的「原因见 X」这类）→ 改成「重点 + 什么时候读 + 路径」。
   - 反过来，**几行就说完的文档**：只被一处指到、两三行能讲清 → 建议并回原处（注释或 rule），删掉文档、入口里的登记行和所有指针。
4. **入口不完整**：
   - 领域索引 rule：领域里既没被某条 rule 指到、又没登记进索引的文档；"什么时候该读"写得含糊；`paths` 没覆盖到这个领域的主要代码。从某条 rule 拆出来、已被那条 rule 指到的文档不用再进索引。
   - 文档入口 `.context/README.md`：挂不到代码上的文档没登记全，或根 CLAUDE.md 没指到它；评估新需求时也该看到的文档（体积、性能预算、外部配额等）只登记在领域索引里；反过来，只在改代码时才用得上的文档也登记进了入口，让入口变长。判断标准见 layout.md「两边都登记」。
   - 孤儿文档按内容定去向：挂得到代码上的，先看能不能并回原处，不能就在相关代码的注释或 rule 里留指针、或登记进领域索引；挂不到的，登记进 `.context/README.md`。
5. **文档内容**：
   - 流水账（一个需求一个文档、只复述某次改动） → 建议删除；夹着有用信息的，把这部分并入对应主题的文档
   - 同一主题散在多个文档里（典型是旧方案一份、新方案一份） → 建议合并成一份描述现状的
   - 与现状矛盾、引用不存在的文件 → `STALE`
   - 实测数字缺日期或测法 → 原文就没写的标 `未记录`，不编造（见 layout.md「项目文档」）
6. **文档结构**（脚本已报出的照单列，补上去向）：文件名带日期或编号前缀 → 改为 `<slug>.md`；放在 `.context/` 顶层、但只属于一个领域的 → 收进 `<领域>/`；领域名和同作用域 `.claude/rules/<领域>/` 不一致 → 统一；嵌套 → 压平；放在 `.claude/` 下、或按类型分目录（`decisions/`、`data/`、`adr/`、旧版插件的 `context/decisions/` 等）的文档 → 迁到 `.context/<领域>/<slug>.md`，**不在 `.context/` 下重建类型目录**。拿不准是不是文档的（目录里有源码或被代码读取的文件），不碰。
7. **skill description 模糊**：看不出"什么时候用"。
8. **已被检查覆盖的文字**：CLAUDE.md、rule 里的某条约束，项目里已有 lint / CI / hook 确定性地检查它（以前标过 `HOOK`、后来检查落地了）→ 建议删掉文字，计划里写明是哪个检查覆盖的。
9. **作用域错位**：monorepo 里只涉及一个包的内容放在了根，或跨包内容放在了某个包里。
10. **空目录、空文件**。

第 3、5、6 项涉及删除、合并、改名、移动（含文档并回原处、单文件 rule 改写成注释）的，计划里逐份列出去向，按 layout.md「移动、改名、删除」列出 grep 到的每处指针和处理方式，并放进「需要拍板」。没发现问题的作用域写一句"无需调整"，不要硬凑改动。

## 阶段五：自动记忆沉淀（可选，用户可整体跳过）

把自动记忆里"换个设备、换个网络也照样成立"的项目知识沉淀进仓库，环境绑定的留在记忆里。

### 定位

1. 系统提示里给了自动记忆目录就直接用它。
2. 没给时：
   - 依次看 `.claude/settings.local.json`、`.claude/settings.json`、`~/.claude/settings.json` 的 `autoMemoryDirectory`，先出现的为准。
   - 否则是 `<配置目录>/projects/<编码后的路径>/memory/`。配置目录默认 `~/.claude`，`CLAUDE_CONFIG_DIR` 非空时用它。路径是**主仓库**根（`git rev-parse --path-format=absolute --git-common-dir` 以 `/.git` 结尾时取其父目录；worktree 共用主仓库那份），不在 git 仓库里时用项目根。编码规则：所有非字母数字字符换成 `-`（`/Users/a/my.app` → `-Users-a-my-app`）。
   - `ls` 确认目录存在。找不到、或情况不在上面几种里（bare 仓库、submodule、路径太长被截断），在计划里列出 `<配置目录>/projects/` 下疑似对应的目录让用户确认，**不要猜**，也不因此中断其他阶段。
3. 读 `MEMORY.md` 和所有 topic 文件，记录每个文件的 `type` 和修改日期。
4. 找出**已沉淀**的条目：内容已出现在默认分支（`git symbolic-ref refs/remotes/origin/HEAD`，取不到就用 `main` / `master`）已提交的文件里（`git grep -F <关键词> <默认分支>`）。这些可以从记忆里删，不再走下面的筛。

### 三道筛

1. **环境相关性**：换台电脑、网络、操作系统还成立吗？`ENV-BOUND` 留在记忆；环境无关的沉淀；有条件成立的沉淀并在第一行写明条件。拿不准的放「需要拍板」，不默认沉淀。
2. **归属**：`type: project` / `reference` 多半属于项目；`user` / `feedback` 多半是 `PERSONAL`，建议去 `~/.claude/CLAUDE.md`，**不直接改那个文件**。以内容为准，与 `type` 不一致时指出来。
3. **按判据阶梯定标签和位置**。

### 敏感信息扫描

自动记忆没经过用户审查。按 layout.md 的敏感信息清单逐条检查，命中的**一律不沉淀**，计划里单列（只说类型和所在文件，不打出值）。

## 查重

每条准备新建的内容，按 layout.md「硬约束」的「新建前先查重」查一遍。有就改那个文件。

## 计划里必须包含

三块，**每一块都要能被用户整体否掉而不影响其他块**。几块指向同一个目标文件（rule、文档、领域索引 rule、`.context/README.md`）时，每块都要能独立创建它：执行时存在就追加，不存在就由当前块创建，只写本块需要的内容。计划里把共享的目标文件标出来。

**跨块条目**：CLAUDE.md 条目或单文件 rule 改写成代码注释，既要删块 A 的原文、又要改块 B 的源码，只做一半会丢内容（只删了原文）或重复（只加了注释）。这类条目连同它的全部动作（加注释、拆出的文档、删原文）只列在块 B，标明"需要 A、B 都批准"；块 A 的分类表里写"见 B"，CLAUDE.md 行数按两块都批准算。A、B 任何一块被否掉，这些条目整条不执行，原文留在原处。

### A. CLAUDE.md、.claude/ 与 .context/ 结构

- 形态、包列表、每个作用域的模式
- 检查脚本的结果摘要（错误/警告数，以及处理方式）
- 按文件分组的分类表：原文摘要（≤20 字）、标签、作用域、目标路径、理由（≤15 字）
- 每条 `PATH-RULE` 和每个领域索引 rule 的 `paths`（单文件 rule 只在文件没法写注释时出现，写明原因），注明相对哪个作用域根
- 体检发现的问题清单
- 每个 CLAUDE.md 的行数：原 → 新
- 最终目录结构树

### B. 代码注释

每处的文件路径 + 行号、原文摘要（≤30 字）、标签、目标路径、原处留下的文案（一句重点和指针）。CLAUDE.md 条目、单文件 rule 改写成注释的也列在这里（跨块条目），写明原文在哪、注释加在哪一行上方。

### C. 自动记忆沉淀

- 记忆总览：文件清单、`type`、行数、修改日期
- 逐条分类表：原文摘要（≤25 字）、来源文件、环境相关性、标签、目标路径、理由（≤15 字）
- 建议去 `~/.claude/CLAUDE.md` 的条目，给出可粘贴的文本
- 敏感信息命中（只列类型和位置）
- 建议从记忆删除的条目（`DERIVABLE` / `STALE` / 已合并进默认分支的）；本次新沉淀的单列为「合并后再删」

### 需要拍板

所有 `STALE`、文档的删除/合并/改名/移动/并回原处、CLAUDE.md 条目或单文件 rule 改写成注释、拿不准形态或归类的、拿不准挂不挂得到代码上的、拿不准该不该搬的注释、有条件成立的记忆条目、建议改成 hook 的规则（写明检查落地前文字放在哪）、已被检查覆盖而建议删掉的文字。

## 批准后执行

1. 先 `git status --untracked-files=no`，已跟踪文件有未提交改动就停下来告诉用户。计划要新建的路径被未跟踪文件占用的，同样停下来。
2. 按计划一次做完所有作用域。用户否掉的块直接跳过；跨块条目在 A、B 任何一块被否掉时整条跳过，原文不动，写进验收报告。
3. **只搬运，不改写。** 原文保留，只允许删纯废话的连接词，不顺手优化措辞，不合并写成两条的规则，不补原文没有的内容。
   - 规范要求的结构性文字照常加：rule 的 frontmatter、rule 里指向文档的路径、领域索引 rule、`.context/README.md` 入口、有条件条目首行的适用条件、文档标题行、代码里的指针、CLAUDE.md 的索引和指路行。
   - 迁移来的数字原文没写日期或测法的标 `未记录`。
   - 例外一：批准的去重上移，目标位置只保留一条原文（选措辞最完整的），计划里列出被合并掉的各处。
   - 例外二：批准的文档合并、文档并回原处、流水账提取，允许重排段落（并回时把"做什么"挪到最前）和加衔接句，但每个事实都要来自原文：仍成立的原样保留，实测数字的历史行保留，被推翻的旧方案删掉（怕有人重新提的留一两句），不新增事实。
   - 例外三：把长注释、单文件 rule、长 rule 拆成「原处一句 + 文档」时，原处那一句（重点）允许从原文压缩，指针里"什么时候读"按代码的实际用途写；扩展内容原样进文档。计划里给出原处的完整文案。
4. **改源码只能增删注释行，一行可执行代码都不许动**，包括格式化，不跑 formatter。整段注释搬走后留下的连续空行，删到只剩一行。
5. 索引和指路行属于块 A：块 A 被否掉时任何 CLAUDE.md 都不动；带参数时只读的 CLAUDE.md 也不动。这两种情况下需要补的，写进验收报告作为建议。
6. 执行块 C 时：
   - **先备份**：整个记忆目录复制到同级的 `memory.bak-<YYYYMMDD-HHMMSS>/`；目标已存在就停下来。
   - **再写入**：沉淀的条目写进目标文件，确认落盘。

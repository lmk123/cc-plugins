# 整理项目上下文

开始前先完整读两份规范，后面所有标签、去处、模板都以它们为准：

- `${CLAUDE_PLUGIN_ROOT}/references/layout.md`：加载机制、记录的单位、准入门槛、去处、判据阶梯、作用域、硬约束、旧版的项目文档、检查脚本
- `${CLAUDE_PLUGIN_ROOT}/references/templates.md`：注释 / rule / skill / CLAUDE.md 索引模板

整理的方向是**删减**：只留 Claude 不知道就会做错的结论，经过、状态、实测流水一律不留（它们在 git 历史里）。体检默认以净减少为目标。

## 工作方式

**两阶段：始终在 plan mode 里调研出计划，用户批准后再执行。批准之前不要创建、修改或删除任何文件。**

- 第一步就确认处于 plan mode。不在的话，先调用 EnterPlanMode 进入（工具只以名字列在延迟工具里时，先用 ToolSearch 加载它），进入后再开始阶段一。
- EnterPlanMode 不可用或用户拒绝进入时，停下来告诉用户切到 plan mode（Shift+Tab）后重新运行本 skill。**不要退回到把计划写进回复里**。
- 计划做完用 ExitPlanMode 提交，用户批准即视为同意执行。
- 计划一次性交出，中间不停下来问。拿不准的全部放进「需要拍板」。

## 范围

- 只处理本仓库内的文件，不读父目录和 `~/.claude/CLAUDE.md`。例外：阶段六的自动记忆目录，以及定位它要读的 settings（只读）。
- 带了参数（`$ARGUMENTS`）就只处理该路径下的 CLAUDE.md、代码注释、`.claude/`、旧版文档目录：
  - 参数是某个包：只写该包的作用域；根的 CLAUDE.md、`.claude/` 只读，用于查重，上移到根的候选只写成建议。
  - 参数是普通目录：拆出来的 rule 写进所属作用域（允许），所属作用域的 CLAUDE.md 只读。
  - 阶段六只沉淀归属于参数范围的记忆条目，其余列一句"不在本次范围"，不动。

## 阶段一：跑检查脚本，判断形态和模式

1. 跑 `node "${CLAUDE_PLUGIN_ROOT}/scripts/check.mjs" "<路径>" --comments`。`<路径>` 是从参数里取出的那一个仓库内路径（参数夹着说明文字的只取路径；拿不准取哪个时不带路径跑，按最窄的合理理解定范围，把范围的歧义写进「需要拍板」，不中途停下来问），加引号传；没带参数就去掉 `"<路径>"`。脚本以退出码 2 报「路径不存在」「路径不在仓库内」时是路径传错了，改正后重跑，不要当成 `node` 不可用。脚本输出是后面几个阶段的输入：rule、`@` import、旧版文档目录和指针这些机械问题以它为准，不用再手工逐条核对。`node` 不可用时在计划里注明，按 layout.md 手工检查。
2. **形态**：按 layout.md「判断形态」定 monorepo 还是单仓库，列出所有包。拿不准写进「需要拍板」，先按单仓库处理。
3. **模式**，按作用域分别判断：
   - **迁移**：没有带 `paths` 的 rule，CLAUDE.md 里混着各种内容。
   - **体检**：已经有带 `paths` 的 rule。
   - 两种模式下，脚本报了「旧版文档目录」「旧版指针」或「旧版领域索引 rule」的作用域都要走阶段四：文档已经不在、只剩指针或索引 rule 的也一样。

计划开头写明形态、包列表、每个作用域的模式，以及哪些作用域有旧版文档、各多少份，哪些只剩指针。

## 阶段二：CLAUDE.md、rule 和 skill 逐条过

1. 找出所有 `CLAUDE.md` / `CLAUDE.local.md`（含 `.claude/CLAUDE.md`），记录行数：以脚本输出的「CLAUDE.md 行数」为准，被 `.gitignore` 忽略的 `CLAUDE.local.md` 也列在里面；Glob、Grep 会跳过被忽略的文件，别靠它们找。`CLAUDE.local.md` 是个人文件，只提建议，不迁移进仓库文件；里面的业务方向是用户选了只留本机的，不建议挪进仓库。脚本报它没被 `.gitignore` 忽略或已经提交进仓库的，写进「需要拍板」。
2. 脚本报了 `.claude/rules/`、`.claude/skills/` 被 `.gitignore` 忽略的作用域，写进「需要拍板」，要写进去的条目标出来，用户解决前不执行。
3. 把每个 CLAUDE.md、每条 rule、每个 skill 的正文和参考文件**逐条**拆开（一条 = 一个独立语义单元），按 layout.md 依次问：
   - **是一条结论吗？** 只讲发生过什么的（经过、时间线、状态、实测流水、推导）→ `DERIVABLE`，删。混着结论和经过的，只留结论和最多一句理由。脚本报的「叙述形态」行要逐行看。
   - **过准入门槛吗？** 没过 → `DERIVABLE`，删。写成「遇到 X 类决策时，先 / 按 Y」的业务方向或决策依据（参考谁、面向谁、什么优先、什么不做），错在判断或建议上，过第 1 条：不要因为它不会让代码出错就删；放得太宽的（只约束包里几片代码却在包级 CLAUDE.md 里）按下一问挪窄，不删。写不成这种结论的产品介绍、背景照常删。
   - **放对地方了吗？** 按判据阶梯定标签和作用域。只匹配一个能写注释的文件的 rule（脚本报「只匹配一个文件」）改写成那个文件里的注释；过长（超过 10 行）、过宽（`paths` 超过 10 项）的 rule 先删，再按「谁需要知道」拆窄；强调泛滥的只给最容易做错的那一处留着。
   - **指向旧版文档的指针**（脚本报「旧版指针」）在阶段四一并处理，这里不单独列。
4. 找**错位**和**重复**：
   - monorepo：2 个及以上包里语义重复的 → 上移到根的候选；根里只对某个包成立的 → 下沉候选；包里其实全仓通用的 → 上移候选。
   - 单仓库：目录级 CLAUDE.md 里全仓通用的 → 上移候选；根里只对某个目录成立的 → 下沉为 rule，那个目录已有目录级 CLAUDE.md 且这条适用其中任何任务时，下沉进那个 CLAUDE.md。
   - 根 CLAUDE.md 里的业务方向：写进去时多半是还没有代码可挂。现在仓库里已经有它约束的那片代码（定价、订阅模块）的 → 下沉候选，按判据阶梯第 5 步定去处。根 `CLAUDE.local.md` 里的同理，下沉到那片代码最近目录的 `CLAUDE.local.md`，不挪进仓库文件。
   - 一事多处：同一件事出现在 CLAUDE.md、rule、注释中的两处以上，只留最近的那一处。
5. **已被检查覆盖**：一条约束已经有测试、lint、CI 或 hook 确定性地检查它 → 建议删掉文字，计划里写明是哪个检查覆盖的。
6. **skill description 模糊**：看不出"什么时候用"。
7. 根 CLAUDE.md 末尾的「更多上下文」索引缺失、缺写入约定那一行、或那一行是旧版插件写的（提到 `context-docs/`、「重点 + 什么时候读 + 路径」）的，按 templates.md 的模板补上或换掉；旧版的「文档入口」那一行在阶段四处理。

## 阶段三：代码注释

候选来自脚本 `--comments` 的输出（长注释块 + 带信号词的注释）。`node` 不可用时，用 Grep 找连续 4 行以上的独立注释块和带"为什么 / 以前 / 注意 / 坑 / 性能 / benchmark / workaround"等词的注释。脚本是机械匹配，命中后逐段读原文判断：

- 讲**这段代码在做什么 / 怎么用** → 留着，别动
- 讲**改这里时必须注意什么**，或**为什么这么选、以前是什么方案、实测数字** → 按阶段二的三问过：只留过了门槛的结论和最多一句理由（`COMMENT`），经过、状态、数字表删掉；整段都过不了的整段删
- 同样的内容在**几个文件**里重复出现 → 合成一条 `PATH-RULE`，各处注释删掉
- 只是复述**某次改动做了什么**，或者是排障经过、时间线 → `DERIVABLE`，删掉
- **流程**（"重新生成这个文件的步骤是……"） → `SKILL`

**绝对不要动**：license header、JSDoc/TSDoc/docstring 等 API 文档注释、`eslint-disable` / `@ts-ignore` / `prettier-ignore` 等有实际功能的注释、类型标注注释、任何行尾注释。只处理独立成段的注释。唯一的例外是这些注释里的旧版指针，在阶段四按那里的办法改。

不要为了瘦身而瘦身：20 行注释讲的全是"这段代码在干嘛"，就该留着。拿不准的列进计划让用户决定。

## 阶段四：迁移旧版文档

脚本报了「旧版文档目录」（`context-docs/`、`.context/`）、「旧版指针」或「旧版领域索引 rule」的作用域走这一阶段。目标是这些目录、指向它们的指针和索引 rule 最终全部清掉，按 layout.md「旧版的项目文档」处理。

**先确认是文档**：`ls` 一遍目录。里面有不是 Markdown 的文件、或有文件被代码 / 工具读取的，那些文件不碰，写进「需要拍板」。

**「疑似按类型分的文档目录」和「放在 `.claude/` 下的文档」**（脚本给的是提示）先看来历：有 CLAUDE.md、rule、注释按「重点 + 路径」指向它的，是更早的插件版本留下的，和旧版文档一样处理。没有的多半是团队自己维护的 ADR 或别的工具的文件，不迁移、不删，在「需要拍板」里提一句由用户确认。

**被代码字符串提到的文档**（脚本报「代码（不是注释）里有 N 行提到旧版文档目录」：日志、报错提示、测试数据里写着文档路径）：删了文档，这些字符串就指空了，而改它们要动可执行代码，不在本 skill 的权限内。这类文档本次不删，写进「需要拍板」：给出每处字符串的位置和建议（把「按 X 文档处理」改成那条结论本身，或者直接去掉路径），由用户自己改，改完下一轮再删文档。文档里的结论照常迁出，指针照常改。只提到整个文档目录、没点名某份文档的行（`.dockerignore`、`.prettierignore` 里的忽略规则，打包命令的 `--exclude`）不挡删除：同样列进「需要拍板」，目录删掉后由用户清理。

**分批**：本次范围内的旧版文档合计超过 30 份时分批。一轮计划合计不超过 30 份左右，所有作用域加在一起算：以领域（`<作用域>/context-docs/<领域>/`）为单位挑，优先选文档少、指针少的；单个领域就超过 30 份的，单独成一轮。其余的列在计划末尾的「下一轮」，按作用域和领域只写份数，不展开。下一轮重新跑 organize-context，从剩下的领域接着做；用户说明是接着迁移的，只做阶段一和阶段四，其余阶段第一轮已经做过，跳过。每个作用域的文档入口、顶层文档和指向整个文档目录的行，留到那个作用域的最后一批。

本批的每份文档：

1. **找出所有指到它的地方**：在整个仓库 grep 文档路径（纯文本路径从仓库根写起），Markdown 链接写的是相对路径，按文件名再 grep 一遍。包括代码注释、rule（含领域索引 rule `context-index.md`）、CLAUDE.md、skill、子代理和命令的定义（`.claude/agents/`、`.claude/commands/`）、文档入口 `README.md`，以及别的 Markdown（项目 README、对外文档，脚本另列为提示「别的 Markdown 里有 N 行提到旧版文档目录」）。CLAUDE.md、rule、skill 的代码块里提到它的不算指针，脚本另列为提示「代码块里有 N 行提到旧版文档目录」，同样要找出来。
2. **读文档**，逐条找出其中的结论（做 X、别做 Y、改 A 同步 B、外部系统的特性），每条过准入门槛：
   - 原处指针的重点里已经有的 → 不用再搬
   - 过了门槛、原处还没有的 → 按判据阶梯定去处，多半是指针所在的那段注释或那条 rule；指针在 skill 里的，多半写进 skill 正文的那一步或 skill 目录下的参考文件；外部系统的特性放到那个系统的配置条目旁边，带观测日期（文档里写了实测日期的取年月，没写的不编）
   - 没过的，以及经过、状态、时间线、实测表格、被否掉方案的论证 → 不迁移
3. **改指针**：每处指针只留「重点」，删掉「什么时候读 + 路径」和括号里对文档内容的说明。重点本身是经过或状态的（「2026-10 起改成 X」「尚未部署」），改写成结论或整句删掉；指针只有路径、没有重点的，整行删掉。
   - 指针写在行尾注释里的（`const MAX = 3; // 见 …`）：只改注释符后面的部分；注释里只剩路径的，连注释符和它前面的空白一起去掉，不留行尾空白。再往前的代码一个字符都不动。
   - 别的 Markdown 里指向它的链接：去掉链接或那半句话，不补别的内容；CHANGELOG 这类历史记录不动。
   - CLAUDE.md、rule、skill 的代码块里提到它的行：是要照着执行的命令（`cat <文档路径>`）就连同那一步一起改掉或删掉；只是示例的不动。
4. **领域索引 rule** 的每一行同上：重点过了门槛的，放到该放的地方（一条窄 rule、某处注释或包级 CLAUDE.md），然后删掉整条索引 rule。
5. **删文档**。别的文档里指向它的链接随那些文档一起处理，不用单独改。

**文档已经不在的指针**（脚本报了「旧版指针」或「旧版领域索引 rule」，指到的文档在磁盘上找不到：用户自己删过，或者上一轮漏改。Markdown 链接先按所在文件的目录解析再判断，`../context-docs/…` 这种相对链接不是找不到）：没有文档可读，也不用分批，本轮一次做完。指针按上面第 3 步改，索引 rule 按第 4 步处理。重点太短、看不出结论的，用 `git log --all -- <文档路径>` 找回原文核对，不为此恢复文档。

最后一批做完时：

- 删掉文档入口 `README.md`。入口里每一行的重点先同上处理：过了门槛的多半是「别做 X」这种硬约束，写进 CLAUDE.md 一行；其余不留。
- 删掉指向整个文档目录、而不是某一份文档的行：根 CLAUDE.md「更多上下文」里指向文档入口的那一行，以及各 CLAUDE.md、rule 里「本包的历史决策在 …」「改口径前先 grep 一遍 …」这类行。按单份文档的路径 grep 不到它们，脚本报的「旧版指针」里会有。
- 删掉空了的文档目录。最后再跑一次脚本，「旧版文档目录」「旧版指针」「旧版领域索引 rule」应该都没有了，「代码块里有 N 行提到旧版文档目录」只剩确认过是示例的。

有指针落在本次不可写的文件里（参数范围之外）的文档，本次不动，只写进建议。

计划里按文档逐份列出：文档路径、指到它的每一处（文件 + 行号）以及改成什么、迁出的每条结论（完整文案）和落点、确认不迁移的内容类别（一句话，如「排障经过、2026-10 的实测表」）。文档已经不在的指针按文件列出：每一处的位置（文件 + 行号）和改成什么。

## 阶段五：其余体检

1. **CLAUDE.md 回胀**：多行条目、段落、带原因的解释、能用 `paths` 限定的内容。
2. **作用域错位**：monorepo 里只涉及一个包的内容放在了根，或跨包内容放在了某个包里。
3. **空目录、空文件**。

没发现问题的作用域写一句"无需调整"，不要硬凑改动。

## 阶段六：自动记忆沉淀（可选，用户可整体跳过）

把自动记忆里"换个设备、换个网络也照样成立"的项目知识沉淀进仓库，环境绑定的留在记忆里。

### 定位

1. 系统提示里给了自动记忆目录就直接用它。
2. 没给时：
   - 依次看 `.claude/settings.local.json`、`.claude/settings.json`、`~/.claude/settings.json` 的 `autoMemoryDirectory`，先出现的为准。
   - 否则是 `<配置目录>/projects/<编码后的路径>/memory/`。配置目录默认 `~/.claude`，`CLAUDE_CONFIG_DIR` 非空时用它。路径是**主仓库**根（`git rev-parse --path-format=absolute --git-common-dir` 以 `/.git` 结尾时取其父目录；worktree 共用主仓库那份），不在 git 仓库里时用项目根。编码规则：所有非字母数字字符换成 `-`（`/Users/a/my.app` → `-Users-a-my-app`）。
   - `ls` 确认目录存在。找不到、或情况不在上面几种里（bare 仓库、submodule、路径太长被截断），在计划里列出 `<配置目录>/projects/` 下疑似对应的目录让用户确认，**不要猜**，也不因此中断其他阶段。
3. 读 `MEMORY.md` 和所有 topic 文件，记录每个文件的 `type` 和修改日期。
4. 找出**已沉淀**的条目：内容已出现在默认分支（`git symbolic-ref refs/remotes/origin/HEAD`，取不到就用 `main` / `master`）已提交的文件里（`git grep -F <关键词> <默认分支>`）。这些可以从记忆里删，不再走下面的筛。

### 三道筛

1. **环境相关性**：换台电脑、网络、操作系统还成立吗？`ENV-BOUND` 留在记忆；环境无关的沉淀；有条件成立的沉淀并在第一句写明条件。拿不准的放「需要拍板」，不默认沉淀。
2. **归属**：`type: project` / `reference` 多半属于项目；`user` / `feedback` 多半是 `PERSONAL`，建议去 `~/.claude/CLAUDE.md`，**不直接改那个文件**。以内容为准，与 `type` 不一致时指出来。
3. **按阶段二的三问**：是结论吗、过门槛吗、放哪。

### 敏感信息扫描

自动记忆没经过用户审查。按 layout.md 的敏感信息清单逐条检查，命中的**一律不沉淀**，计划里单列（只说类型和所在文件，不打出值）。

## 查重

每条准备新建的内容，按 layout.md「硬约束」的「新建前先查重」查一遍。有就改那个文件。

## 计划里必须包含

三块，**每一块都要能被用户整体否掉而不影响其他块**。几块指向同一个目标文件（rule、CLAUDE.md）时，每块都要能独立创建它：执行时存在就追加，不存在就由当前块创建，只写本块需要的内容。计划里把共享的目标文件标出来。

**跨块条目**：往源码注释里**加内容**的（CLAUDE.md 条目、单文件 rule 改写成注释，从旧版文档迁出结论写进注释），既要改块 A 的文件、又要改块 B 的源码，只做一半会丢内容或重复。这类条目连同它的全部动作只列在块 B，标明"需要 A、B 都批准"；块 A 里写"见 B"。A、B 任何一块被否掉，这些条目整条不执行，原文留在原处；涉及的旧版文档本次也不删。

只删改源码注释里的旧版指针（删掉「什么时候读 + 路径」、改写叙述形态的重点）归到文档所在的块 A，不算跨块条目。

### A. CLAUDE.md、.claude/ 与旧版文档

- 形态、包列表、每个作用域的模式
- 检查脚本的结果摘要（错误/警告数、修剪候选数、旧版文档数和指针数，以及处理方式）
- 删除清单：逐条列出要删的 CLAUDE.md 条目、rule 行、rule、skill 内容，每条写明是哪一问没过（不是结论 / 没过门槛的哪一条 / 已被检查覆盖）
- 按文件分组的分类表：原文摘要（≤20 字）、标签、作用域、目标路径、理由（≤15 字）
- 每条新建、改写的 `PATH-RULE` 的完整正文和 `paths`（单文件 rule 只在文件没法写注释时出现，写明原因），注明相对哪个作用域根
- 旧版文档迁移（阶段四）：按文档逐份列出；分了批的，末尾列出「下一轮」的领域和份数
- 每个 CLAUDE.md 的行数：原 → 新；每个作用域的 rule 条数和正文行数、旧版文档数、旧版指针数：原 → 新（取脚本开头的规模汇总，整理后的按计划推算）
- 最终目录结构树

### B. 代码注释

每处的文件路径 + 行号、原文摘要（≤30 字）、标签、改后的完整文案。跨块条目也列在这里，写明内容来自哪里（CLAUDE.md 条目、单文件 rule、旧版文档）、加在哪一行上方。

### C. 自动记忆沉淀

- 记忆总览：文件清单、`type`、行数、修改日期
- 逐条分类表：原文摘要（≤25 字）、来源文件、环境相关性、标签、目标路径、理由（≤15 字）
- 建议去 `~/.claude/CLAUDE.md` 的条目，给出可粘贴的文本
- 敏感信息命中（只列类型和位置）
- 建议从记忆删除的条目（`DERIVABLE` / `STALE` / 已合并进默认分支的）；本次新沉淀的单列为「合并后再删」

### 需要拍板

删除清单、所有 `STALE`、旧版文档的迁移和删除、CLAUDE.md 条目或单文件 rule 改写成注释、拿不准形态或归类的、拿不准该不该删的注释和结论、被代码读取的旧版文档目录里的文件、「疑似按类型分的文档目录」和「放在 `.claude/` 下的文档」是不是旧版文档、有条件成立的记忆条目、建议改成 hook 的规则（写明检查落地前文字放在哪）、已被检查覆盖而建议删掉的文字、业务方向留在仓库还是挪进本地 `CLAUDE.local.md`（从自动记忆沉淀的同样要问；已提交过的，git 历史里仍看得到）。

## 批准后执行

1. 先 `git status --untracked-files=no`，已跟踪文件有未提交改动就停下来告诉用户。计划要新建的路径被未跟踪文件占用的，同样停下来。
2. 按计划一次做完所有作用域（阶段四分了批的，只做本轮的领域）。用户否掉的块直接跳过；跨块条目在 A、B 任何一块被否掉时整条跳过，原文不动，写进验收报告。
3. **只搬运和删减，不改写。** 留下的原文不顺手优化措辞，不合并写成两条的规则，不补原文没有的内容。例外：
   - 规范要求的结构性文字照常加：rule 的 frontmatter、有条件条目首句的适用条件、CLAUDE.md 的索引小节。
   - 一条内容里混着结论和经过的，删掉经过；删完句子不通的，只补连接词。
   - 从旧版文档迁出的结论、改写叙述形态的重点、合并的重复条目，允许从原文压缩成一句结论，但每个事实都要来自原文，不新增事实。计划里给出完整文案。
   - 批准删除的直接删，不迁移、不建归档目录。删除靠 git 留底。
4. **改源码只能动注释，可执行代码一个字符都不许动**，包括格式化，不跑 formatter。能做的只有两种：增删、改写整行的注释；行尾注释里的旧版指针，只改注释符后面的部分（整个行尾注释去掉时，连注释符前面的空白一起去掉）。整段注释删掉后留下的连续空行，删到只剩一行。
5. 索引小节属于块 A：块 A 被否掉时任何 CLAUDE.md 都不动；带参数时只读的 CLAUDE.md 也不动。这两种情况下需要补的，写进验收报告作为建议。
6. 执行块 C 时：
   - **先备份**：整个记忆目录复制到同级的 `memory.bak-<YYYYMMDD-HHMMSS>/`；目标已存在就停下来。
   - **再写入**：沉淀的条目写进目标文件，确认落盘。
   - **最后删除**：只删 `DERIVABLE` / `STALE` 和已合并进默认分支的条目。**刚沉淀的本次不删**：记忆由同一仓库的所有 worktree 共用，而沉淀内容此刻只在当前 worktree 的未提交改动里。同步更新 `MEMORY.md`，清空的 topic 文件删掉并移除索引行。`ENV-BOUND` 原样保留。
7. 不碰 `~/.claude/CLAUDE.md` 和任何 `settings.json`。不自动 commit。

## 验收报告

做完后一次性输出：

1. `git diff --stat`
2. **再跑一次检查脚本**，贴出汇总行；本次引入的错误要修掉，剩下的警告和修剪候选逐条说明为什么保留。本批迁移过的文档，脚本不应再报指向它们的旧版指针
3. **整理前后的规模**：每个作用域的 rule 条数和正文行数、旧版文档数、旧版指针数，原 → 新；每个 CLAUDE.md 的行数，原 → 新
4. **结论守恒自检**：计划里标为保留、迁出的每条结论，在新位置都能找到吗？列出任何丢失的。批准删除的单独列出，说明已删
5. **源码零改动自检**：对所有改过的源码文件跑 `git diff -U0 -- <文件>`，确认 `+`/`-` 行都是注释行或允许删的空行；改了行尾注释的行，注释符之前的部分要和原来逐字相同（整个行尾注释去掉的，只少了注释符前面的空白）。有其他变化就明确指出——这是 bug
6. 执行了块 C 时：记忆目录前后的文件数与 `MEMORY.md` 行数、`ENV-BOUND` 保留条数、备份路径、「合并后再删」清单
7. 与计划的偏差，以及原因；分了批的，提醒用户下一轮从哪些领域接着做，重跑时说明是接着迁移的就只做迁移

# 记录上下文

下面是日常记录够用的全部规则。碰到这里没覆盖的情况（判断形态、目录级 CLAUDE.md、敏感信息清单等），读 `${CLAUDE_PLUGIN_ROOT}/references/layout.md` 对应一节；要新建文件时照 `${CLAUDE_PLUGIN_ROOT}/references/templates.md` 的模板写。

## 1. 值不值得记

**同时满足**两条才记：

- **本次会话真正验证过**：实际跑过、读代码确认过、或用户明确说的。不记推测。
- **下次会重新踩**：读一遍代码就知道的不记；"这次做了什么、改了哪些文件"不记，那是 commit 的职责。值得记的是：为什么非这么做不可、试过什么不行、实测出来的数字、外部系统的限制、碰到某些文件时必须注意的事。commit message 里写过也照样记——Claude 平时不翻 git 历史。

一次任务最多记三条，想记的更多说明在记流水账，挑最重要的三条。不确定就问用户。

## 2. 属不属于项目

- 个人偏好、对你的纠正、个人习惯 → 不进仓库，写自动记忆。用户想对所有项目生效时，给一行可粘贴到 `~/.claude/CLAUDE.md` 的文本，不直接改那个文件。
- 换台电脑、换个网络就不成立的（本机路径、本机版本、端口、代理、凭据） → 不进仓库，写自动记忆。
- 有条件成立的（"仅 macOS""Node 20 以下"） → 属于项目，正文第一行写明条件。
- 含 API key、token、密码、内网地址、私有仓库地址、带用户名的绝对路径等敏感信息 → 一律不进仓库。

属于项目的知识**不要只记进自动记忆**：那里只对你自己这台机器生效，队友和其他 worktree 看不到。

## 3. 写成什么

按顺序问，第一个"是"就停。一条内容混着"做什么"和"为什么"时先拆开，各自走一遍：

1. 能用 lint / CI / hook 自动校验吗？能 → 建议用户加检查，但**不停**，照常往下走把文字写好；用户确认检查加上后才删文字
2. 是有步骤、平时用不上的流程吗？是 → **skill**：`.claude/skills/<name>/SKILL.md`，description 写清什么时候用
3. 是背景（原因、经过、数字、外部约束），不是"做什么"吗？是 → **文档**：`.context/<领域>/<slug>.md`
4. 是"做什么"，且只在碰到特定文件 / 目录时才需要知道吗（"改 A 必须同步 B"、某模块的坑）？是 → **rule**：`.claude/rules/<领域>/<name>.md`，带 `paths`
5. 剩下的是任何任务都可能违反的硬约束 → **CLAUDE.md**，只写一行，不带原因

**代码注释不是记背景的地方。** 想写超过一两行解释"为什么"的注释时，背景写成文档，注释最多留一行：这个位置确有讲究（顺序不能换、数值不能随便改）时，写清讲究 + 文档路径，例如 `// 重试次数不能超过 3，原因见 apps/web/.context/api/retry-policy.md`；纯背景就不留。

## 4. 写到哪个作用域

- 单仓库：一律仓库根的 `.claude/`、`.context/`。
- monorepo（判断信号见 layout.md「判断形态」）：涉及的文件全在某个包内 → 该包的 `.claude/`、`.context/`；涉及两个及以上包 → 仓库根。
- `.context/` 被 `.gitignore` 忽略、或被别的用途占用时，停下来告诉用户。

**领域**（`<领域>`）取项目已有叫法：先看同作用域 `.claude/rules/` 下已有的领域目录名，其次用代码里的模块名、目录名，不自造。说不清属于哪块、或跨两块以上的文档放 `.context/` 顶层。第一份文档就放进领域目录。

**文件名**用 `<slug>.md`，英文小写短横线概括主题（`retry-policy`），不带日期、不带编号。

## 5. 先查重

`ls` 目标目录，再按 slug 和主题关键词 grep **整个仓库**的 `.claude/`、`.context/`（显式传路径，点开头的目录有些工具默认跳过）和所有 CLAUDE.md。有同主题的就**改那份**，让它描述现状（情况变了原地改写，不追加"更新：……"，不改文件名）；它在别的作用域、而这次的内容让归属变了的，照样改那份，并告诉用户，挪动交给 organize-context。不挪动、不改名已有文件。

## 6. 写文档时

- 第一行是标题。写现状，不写流水账。
- 实测数字带日期和测法；同一指标的新值追加一行，不覆盖旧值（表格见模板）。
- "做什么"的部分写成 rule，rule 正文留一行仓库根起的路径指向文档。
- **登记进领域索引 rule**：`<作用域>/.claude/rules/<领域>/context-index.md` 里加一行「路径：什么时候该读」。还没有这个文件就照模板新建，`paths` 覆盖这个领域的代码（如 `src/api/**`，不能宽到 `src/**`）。顶层的跨领域文档，登记进每个相关领域的索引。不登记的文档以后基本不会被读到。

## 7. 写 rule 时

- frontmatter 的 `---` 必须是第一行。
- `paths` 相对 rule 所属作用域的根写（包内 rule 相对包目录），要窄，至少匹配到一个现存文件。
- 正文写"做什么"，一句话能说完的原因跟在后面，说不完的进文档。

## 8. 补 CLAUDE.md 的指路

根 CLAUDE.md 末尾的「更多上下文」索引缺「项目文档」或「写入约定」那两行时，按模板补上（不管这是不是第一份文档）。根还没有 CLAUDE.md 时，新建一个只含这个索引的。包级 CLAUDE.md 所在的包有自己的 `.context/` 时，末尾要有一行指路；包还没有 CLAUDE.md 的不为此新建。

## 9. 写完之后

1. 跑一次 `node "${CLAUDE_PLUGIN_ROOT}/scripts/check.mjs" <作用域路径>`，修掉本次引入的错误（`paths` 匹配不到、指针失效、孤儿文档等）。之前就有的问题不在这次处理，提醒用户跑 organize-context。`node` 不可用就跳过。
2. 在回复末尾用一行告诉用户写到了哪些文件（含顺带改的索引 rule、CLAUDE.md），例如：

   > 记了一条：`apps/web/.context/api/retry-policy.md`（已登记进 `apps/web/.claude/rules/api/context-index.md`）

不要静默写入，否则这套结构会重新变成没人看的黑箱。

## 不要做的事

- 同一件事写进两个地方
- 用 `@path` import 引用文件
- 改 `~/.claude/CLAUDE.md`、`~/.claude/settings.json`

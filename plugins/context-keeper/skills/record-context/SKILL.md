# 记录上下文

下面是日常记录够用的全部规则。碰到这里没覆盖的情况（判断形态、目录级 CLAUDE.md、敏感信息清单等），读 `${CLAUDE_PLUGIN_ROOT}/references/layout.md` 对应一节；要新建文件时照 `${CLAUDE_PLUGIN_ROOT}/references/templates.md` 的模板写。

## 1. 先写成一条结论

把要记的东西改写成一条面向以后的结论：做 X、别做 Y、改 A 要同步 B，或者外部系统的「症状 → 原因 → 怎么办」。理由最多一句，只在它能让人判断结论什么时候不再成立、或者防止结论被当成多余的东西删掉时才写。

写不成结论的不记：经过和时间线、状态（「已上线」「尚未部署」「待办」）、实测流水和表格、被否掉方案的完整论证、推导过程、「这次改了什么」。它们写进 commit message 或 PR 描述，仓库文件里不写，也不留指向它们的指针。

判断办法：这句话是在告诉下一个 Claude **怎么做**，还是在讲**发生过什么**？去掉理由，它还会照着做吗？会的话理由也删掉。

日期只用来给外部系统的事实标观测时间（「2026-11 实测：…」），不用来记经过。

## 2. 过准入门槛

同时满足四条才记：

1. **有具体的错**：写得出一句「不知道这条，Claude 会做 X，结果是 Y」。X 也可以是一个判断或建议：偏离用户定下的方向、漏看该参考的对象。「了解背景有帮助」「以后可能用得上」不算。
2. **读仓库推不出来，或重新弄清代价高**：读那几行代码、配置、测试就知道的不记。
3. **拦不住**：类型检查、测试、lint、CI、构建失败、运行时报错都拦不下。
4. **静默或代价高**：错了不报错，或者代价高、难回滚（线上事故、账单、数据损坏、对外发布）。

先问自己它是怎么来的：

- **本次会话里被纠正过**（用户说「不对，应该……」，或真实环境出了错：部署失败、线上数据不对、外部站点和代码的假设不一样）→ 多半过得了，照下面写。
- **外部系统的实测结果**（站点怪癖、要带的特殊参数、配额）→ 多半过得了，写在那个系统的配置条目旁边，带观测日期。
- **还没错过、但错了不可逆** → 过得了，写。
- **用户给出的业务方向或决策依据**（参考谁、面向谁、什么优先、什么不做）→ 过得了：读代码推不出来，而且只有用户说了算。仍要写成「遇到 X 类决策时，先 / 按 Y」，X 取自用户的话或正在做的决策，不替用户补；补不出来时回复「不记」，并问一句它影响哪类决策，用户答得出就照答案写。产品介绍、历史沿革、公司背景这类说不出影响哪类决策的不记。
- **Claude 自己读代码、跑命令查出来的** → 下一个 Claude 也查得出来，不记。

拿不准时不记。

- 没过：不写。回复一句「不记：<没过哪一条>」，需要的话把经过写进 commit message 或 PR 描述。
- 用户坚持要记：照记，在回复里点明没过哪一条。放宽的只是这四条，第 1 节写不成结论的经过、状态照样不记；业务方向本来就过门槛，坚持也绕不过「遇到 X 类决策时」这个写法，X 还是要用户给。

一次任务最多记三条，想记的更多说明在记流水账，挑最重要的三条。

被 comment-hook 提醒有长注释块而来的：只留一条结论和最多一句理由，经过、状态、数字表直接删；整段都过不了门槛的整段删。这不占"最多三条"。

## 3. 属不属于项目

- 个人偏好、个人习惯 → 不进仓库，写自动记忆。用户想对所有项目生效时，给一行可粘贴到 `~/.claude/CLAUDE.md` 的文本，不直接改那个文件。
- 换台电脑、换个网络就不成立的（本机路径、本机版本、端口、代理、凭据） → 不进仓库，写自动记忆。
- 有条件成立的（"仅 macOS""Node 20 以下"） → 属于项目，第一句写明条件。
- 含 API key、token、密码、内网地址、私有仓库地址、带用户名的绝对路径等敏感信息 → 一律不进仓库。
- 业务方向和决策依据 → 公不公开由用户定，写之前先问一句（用户已经说了放哪的不问）：进仓库，按第 4 节写；只留本机，写一行进 `CLAUDE.local.md`，放在它约束的那片代码最近的目录里（跨几片目录的放最近的共同上级，还没有代码可挂的放仓库根，代码出现后挪过去）。问的时候说清代价：队友、别的 worktree、别的机器都看不到，放到仓库根的会常驻加载。写之前确认它进不了仓库：不是 git 仓库的直接写；`git ls-files <路径>` 有输出就是已经提交过，停下来告诉用户先 `git rm --cached`；`git check-ignore -q <路径>` 退出码是 1 就是没被忽略，停下来告诉用户在 `.gitignore` 里加一行。

属于项目的知识**不要只记进自动记忆**：那里只对你自己这台机器生效，队友和其他 worktree 看不到。

## 4. 写到哪

按顺序问，第一个"是"就停：

1. 能用 lint / 测试 / CI / hook 自动校验吗？能 → 建议用户加检查，但**不停**，照常往下走把文字写好。文字本次不删：告诉用户检查落地后可以自己删掉这条，或下次用户跑 `/context-keeper:organize-context` 时由体检列出来
2. 是有步骤、平时用不上的流程吗？是 → **skill**：`.claude/skills/<name>/SKILL.md`，description 写清什么时候用
3. 只在碰到特定文件 / 目录时才需要知道吗？是 →
   - 适用于某个包内任何任务（monorepo），或某个已有目录级 CLAUDE.md 所在目录内任何任务 → 写一行进那个包或目录的 CLAUDE.md（包还没有 CLAUDE.md 就新建；不为此新建目录级 CLAUDE.md），不写成覆盖整个包 / 目录的宽 rule
   - 只涉及**一个文件**、且这个文件能写注释 → **代码注释**，写在相关的函数、常量、配置条目上方，涉及整个文件的写在文件头，1–3 行
   - 涉及**多个文件**（一类文件的约定、一个目录的坑、"改 A 必须同步 B"），或文件没法写注释（JSON、lockfile、生成物、二进制资源）→ **rule**：`.claude/rules/<领域>/<name>.md`，带 `paths`，"做什么"在前，最多一句理由，正文不超过 10 行
   - "涉及几个文件"按**谁需要知道**算：约束的是调用方的（"必须在 X 之后调用"），涉及的是调用它的那些文件。调用方分散 → 写进定义处的 API 文档注释（JSDoc / docstring）；调用方集中在某个目录 → `paths` 覆盖调用方的 rule
   - 某个外部站点、供应商、接口自己的特性 → 写在它自己的配置条目旁边，不攒进一条覆盖所有站点的 rule
   - 业务方向或决策依据 → 挂在它约束的那片代码上，按约束范围定：约束整个包（或某个已有目录级 CLAUDE.md 所在目录）、那里任何任务都可能用上的，写一行进那个 CLAUDE.md；只约束几片代码（定价、订阅模块）的，不论跨不跨包，写成 `paths` 只覆盖那几片的 rule
4. 剩下的是任何任务都可能违反的硬约束，或还没有任何代码可挂的业务方向（代码出现后再挪）→ **根 CLAUDE.md**（`CLAUDE.md` 或 `.claude/CLAUDE.md`，哪个已存在写哪个），只写一行，不带原因
5. 都不是（挂不到代码上、又不是硬约束，比如评估过但没做的需求、以后可能要做的功能）→ 不记

**写不下的**（注释超过 3 行、rule 超过 10 行）：不挪到别处，先删经过、状态、数字表和重复的话。删完还写不下，按「谁需要知道」拆成几处，或者是流程就写成 skill，是每次都要重做的测量、核对就建议写成脚本或测试。

## 5. 写到哪个作用域

- 单仓库：一律仓库根的 `.claude/`。
- monorepo（判断信号见 layout.md「判断形态」）：涉及的文件全在某个包内 → 该包的 `.claude/`；涉及两个及以上包 → 仓库根。
- 往 `.claude/` 新建文件之前，对每个要新建的路径跑 `git check-ignore -q "<路径>"`（如 `apps/web/.claude/rules/api/retry.md`）：退出码为 0 表示会被 `.gitignore` 忽略，写进去队友也看不到，停下来告诉用户。
- 动手写之前先跑一次检查脚本留基线（见第 8 节）。

**领域**（`<领域>`）取项目已有叫法：先看同作用域 `.claude/rules/` 下已有的领域目录名，其次用代码里的模块名、目录名，不自造。**文件名**用英文小写短横线概括主题（`retry-policy`），不带日期、不带编号。

## 6. 先查重

按主题关键词 grep **整个仓库**的 `.claude/`（显式传路径，点开头的目录有些工具默认跳过）、所有 CLAUDE.md 和相关代码的注释。有同主题的就**改那条**，让它描述现状（情况变了原地改写，不追加"更新：……"）；它在别的作用域、而这次的内容让归属变了的，照样改那条，并告诉用户，挪动留给用户跑 `/context-keeper:organize-context`。

**改动让已记下的结论不再成立**（改了注释里提到的数值、换掉了 rule 约束的那段代码）：在同一次改动里改成现状；现在拦得住了（加了测试、lint、类型）或者不再需要的，直接删。这不用过第 2 节的筛，也不占"最多三条"。

## 7. 写注释和 rule 时

注释：

- 紧贴相关代码，1–3 行。只改注释行，不动任何可执行代码。
- 涉及整个文件的写在文件头，和下面的代码之间空一行（后面紧跟 import 的不用）。
- 不写指针：不写「详见 X」「见 PR #123」。
- 讲"这段代码在做什么、怎么用"的注释不归本 skill 管，照常写。

rule：

- frontmatter 的 `---` 必须是第一行。
- `paths` 相对 rule 所属作用域的根写（包内 rule 相对包目录），要窄，至少匹配到一个现存文件。只匹配到一个能写注释的文件时，改写成注释。
- 正文"做什么"在前，最多一句理由跟在后面，不超过 10 行（不算 frontmatter 和空行）。⚠️ 和加粗最多两处。

## 8. 写完之后

1. **写入前**先跑一次 `node "${CLAUDE_PLUGIN_ROOT}/scripts/check.mjs" "<作用域路径>"`（仓库根作用域不传路径）记下结果作为基线，**写完后**再跑一次。脚本以退出码 2 报「路径不存在」「路径不在仓库内」时是路径传错了，改正后重跑，不要当成 `node` 不可用。基线里没有的就是本次引入的（`paths` 匹配不到、rule 过长、单文件 rule、`.claude/` 被忽略等），修掉。例外：脚本报「只匹配一个文件」、而那个文件是生成物或写了注释会被工具覆盖的，rule 是对的，保留，在回复里说明一句。基线里就有的不在这次处理；报了旧版文档目录或旧版指针的，提醒用户跑 `/context-keeper:organize-context`。`node` 不可用就跳过。
2. 在回复末尾用一行告诉用户写到了哪些文件，例如：

   > 记了一条：`apps/web/src/api/retry.ts` 的注释

   > 记了一条：`apps/web/.claude/rules/styling/tokens.md`

   > 不记：读代码就能看出来（门槛第 2 条），经过写进了 commit message

不要静默写入，也不要静默不记，否则这套结构会重新变成没人看的黑箱。

## 不要做的事

- 同一件事写进两个地方
- 新建文档目录（`context-docs/`、`docs/decisions/` 之类）来放经过和数据
- 用 `@path` import 引用文件
- 改 `~/.claude/CLAUDE.md`、`~/.claude/settings.json`

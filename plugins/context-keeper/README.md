# context-keeper

只把 Claude 不知道就会做错的事记进项目，写在它用得上时一定会看到的地方：单个文件的写成紧贴代码的短注释，几个文件共用的写成 rule，流程写成 skill，硬约束才进 CLAUDE.md。经过、历史、实测流水留在 commit 和 PR 里，不进仓库文件。兼容 monorepo 与单仓库。

## 它解决什么

不加约束时，Claude 会把项目知识往几个地方堆：

- **CLAUDE.md**：每条都常驻，越写越长，大部分内容和当前任务无关。
- **代码注释**：为什么这么写、以前的方案、实测数字，一段段写在代码里，读代码的人被迫看一遍。
- **rule 和文档**：每做一个需求、每排一次障，就落一份记录，攒成一个越来越大的历史包袱。

这些内容里，真正能让下一个 Claude 少犯错的只是一小部分。context-keeper 只留这一部分，其余的交给 git。

## 只记一种东西：结论

仓库里记下的每一条都是一条面向以后的结论：做 X、别做 Y、改 A 要同步 B，或者外部系统的「症状 → 原因 → 怎么办」。理由最多一句，只在它能帮人判断结论什么时候不再成立、或者防止结论被当成多余的东西删掉时才写。

经过、时间线、状态（「已上线」「尚未部署」）、实测流水、被否掉方案的论证都不写：它们照常写在 commit message 和 PR 描述里，代码里也不留指向它们的指针。想知道某段代码为什么这样写，`git blame` 从那几行就能找到对应的提交和 PR。

## 值不值得记

一条结论同时满足四条才记：

1. **有具体的错**：说得出「不知道这条，Claude 会做 X，结果是 Y」。X 也可以是一个判断或建议，比如偏离用户定下的方向、漏看该参考的竞品
2. **读仓库推不出来，或重新弄清代价高**：业务约定、仓库设置、外部系统的行为这类读代码看不出来的
3. **拦不住**：类型检查、测试、lint、CI、运行时报错都拦不下
4. **静默或代价高**：错了不报错，或者是线上事故、账单、数据损坏这类难回滚的

最常见的来源是：用户在会话里纠正过的做法，真实环境出过的错，外部系统的实测特性，一旦出错就无法挽回的操作，还有用户定下的业务方向（写成「遇到 X 类决策时，先 / 按 Y」；公不公开先问用户，不公开的写进被 `.gitignore` 忽略的 `CLAUDE.local.md`）。Claude 自己读代码查出来的不记，下一个 Claude 也查得出来。

拿不准时不记：漏记一条，代价是某次多查几分钟，或者被用户再纠正一次；多记一条，代价是永久的。

## 放在哪

| 内容 | 去处 | 什么时候进 context |
| --- | --- | --- |
| 任何任务都可能违反的硬约束 | `CLAUDE.md`，一条一行 | 一直 |
| 只和一个文件（或其中一段代码、一个配置条目）有关的 | 代码注释，紧贴相关代码，1–3 行 | 读到那段代码时 |
| 几个文件共用的（一类文件的约定、一个目录的坑、"改 A 必须同步 B"），或没法写注释的文件（JSON、lockfile、生成物） | `.claude/rules/<领域>/<name>.md`，带 `paths:`，不超过 10 行 | 读/改到匹配文件时 |
| 有步骤的流程 | `.claude/skills/<name>/SKILL.md` | 启动时只有 description |
| 个人偏好 / 环境绑定 | 不进仓库，留在自动记忆 | — |

没有别的去处。写不下的（注释超过 3 行、rule 超过 10 行）先删经过和数字；还写不下，就是几件事混在了一起，按「谁需要知道」拆开，或者写成 skill、脚本。

monorepo 中，只涉及一个包的内容放进该包自己的 `CLAUDE.md`、`.claude/`，跨包内容放在仓库根。

### 为什么单个文件不用 rule

`paths` 只匹配一个文件的 rule，碰到这个文件就整条加载，Claude 只读文件的一部分时也一样，所以它在 token 上和写在文件里的注释没区别，反而离代码更远、定位不到函数。rule 的优势在于一条覆盖很多文件，所以只留给几个文件共用的内容。

### 外部系统的特性写在哪

写在那个系统自己的配置条目旁边，带上观测日期：

```ts
  {
    // 2026-11 实测：429 是业务报错（余额或分组问题），不是限流，别按限流退避重试
    site: 'example-relay',
```

下次碰到这个站，Claude 一定会读它的配置，知识就在眼前。日期告诉读的人这条还有多可信：外部系统随时会变，对不上了就该重测。

## 怎么起作用

**写入端**

- `record-context`：要记一条项目知识时，先判断它是不是一条结论、过不过门槛，再决定写到哪里。
- 根 CLAUDE.md 的「更多上下文」里有一行常驻的写入约定，让 Claude 默认不把背景写成长注释、文档，也不只记在自动记忆里。
- comment hook（PostToolUse）：Claude 写入 4 行以上的独立注释块时，提醒它注释只留一条结论和最多一句理由，经过留给 commit 和 PR。只提醒、不阻断，JSDoc、license、行尾注释不算。设环境变量 `CONTEXT_KEEPER_COMMENT_HOOK=0` 可关闭。

**读取端**

不需要额外的机制：注释在读到那段代码时就在眼前，rule 在碰到匹配的文件时自动加载，CLAUDE.md 一直在。

**整理与体检**

- `/context-keeper:organize-context`：只能由你手动输入调用，Claude 不会自行触发。把现有项目整理成这套结构，已经在用的项目则做体检，默认以删减为目标。也会把旧版插件留下的 `context-docs/` 迁走：过得了门槛的结论放回原处，其余随文档一起删掉。始终在 plan mode 里出计划（不在会先进入），批准后才动文件。也能把自动记忆里与环境无关的内容沉淀进项目。
- `scripts/check.mjs`：确定性检查，skill 会自动调用，也可以手动跑：

  ```bash
  node <插件目录>/scripts/check.mjs [路径] [--comments]
  ```

  检查 rule 的 `paths` 是否生效、rule 是否过长、单文件 rule、`@` import、CLAUDE.md 里带原因的行、`.claude/rules/` 和 `.claude/skills/` 有没有被 `.gitignore` 忽略、`CLAUDE.local.md` 有没有漏忽略或已经提交进仓库、旧版的文档目录和指向它的指针（代码块、代码字符串、别的 Markdown 里提到它的另列提示）；另列一块「修剪候选」（过宽的 rule、强调泛滥、带日期和状态的叙述），开头给出每个作用域的规模。有错误时退出码为 1。没有依赖，接 CI 时把 `check.mjs` 连同 `lib/` 目录一起复制进项目。

## 改造前后

改造前，`apps/web/src/api/retry.ts`：

```ts
// 重试次数固定为 3。以前是 5 次，但上游网关连续 5 次失败
// 会把客户端 IP 拉黑 10 分钟，线上出过一次事故。
// 首次 + 3 次重试 = 4 次，留一次余量。
// 试过在网关前加熔断，和网关限流叠加后导致长时间不可用，放弃了。
// 退避从 200ms 起指数增长。
const MAX_RETRY = 3;
```

改造后：

```ts
// 重试上限 3：网关连续 5 次失败会封 IP 10 分钟（首次 + 3 次重试，留一次余量）
// 别在网关前加熔断：和网关限流叠加后会长时间不可用
const MAX_RETRY = 3;
```

"以前是 5 次、出过一次事故"是经过，留给 commit；熔断方案怕有人重新提，写成一条「别做」；退避读代码就看得出来，删掉。

## 从 0.9.x 及更早版本升级

0.10.0 取消了项目文档目录 `context-docs/`，以及围绕它的指针、领域索引 rule、文档入口、pointer-guard hook 和 doc hook。

原因：文档目录让「记下来」显得没有成本，用插件整理过的项目，文档只增不减，大半是排障经过、上线状态和实测流水，成了一个越来越大的历史包袱。这些内容 commit 和 PR 本来就有，真正需要留下的结论写在原处就够了。

- 规范：记录的单位改成「一条结论」，准入门槛加上「读仓库推不出来」；去处只剩 CLAUDE.md、注释、rule、skill；不再写指针
- `record-context`：经过、状态、流水不进仓库；不再建文档
- `organize-context`：迁移旧文档：每份文档里过得了门槛、原处还没有的结论放回原处，其余随文档删掉；指针只留重点，删掉「什么时候读 + 路径」；领域索引 rule 和文档入口逐行重过门槛后删掉。文档多的项目按领域分批
- 检查脚本：去掉文档、指针、入口相关的检查；新增「旧版文档目录」「旧版指针」和修剪候选「叙述形态」
- hook：删掉 pointer-guard 和 doc hook，只留 comment hook

升级后跑一次 `/context-keeper:organize-context`，它会按领域列出迁移计划，批准后执行。删掉的文档留在 git 历史里，`git log --all -- <文档路径>` 找得回来。

完整规范见 [references/layout.md](references/layout.md)，模板见 [references/templates.md](references/templates.md)。

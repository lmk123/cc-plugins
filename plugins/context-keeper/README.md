# context-keeper

整理与沉淀项目上下文：CLAUDE.md 的常驻部分尽量小；读代码得不到的知识放在离用到它的代码最近的地方——单个文件的写成紧贴代码的短注释，几个文件共用的写成 rule；历史、数据、详细经过等扩展内容进项目文档（`.context/`），原处只留「一句话重点 + 什么时候读 + 路径」的指针，由 Claude 按需读。兼容 monorepo 与单仓库。

## 它解决什么

不加约束时，项目知识会往两个地方堆：

- **CLAUDE.md**：每条都常驻，越写越长，大部分内容和当前任务无关。
- **代码注释**：为什么这么写、以前的方案、实测数字，一段段写在代码里。一个文件 10 个函数，这次只改其中一个，另外 9 个函数的历史也跟着进了 context，读代码的人也被迫看一遍。

context-keeper 把这些内容按"什么时候需要知道"分流：

| 内容 | 去处 | 什么时候进 context |
| --- | --- | --- |
| 任何任务都可能违反的硬约束 | `CLAUDE.md`，一条一行 | 一直 |
| 只和一个文件（或其中一段代码）有关的：做什么、坑、一句原因 | 代码注释，紧贴相关代码，1–3 行 | 读到那段代码时 |
| 几个文件共用的（一类文件的约定、一个目录的坑、"改 A 必须同步 B"），或没法写注释的文件（JSON、lockfile、生成物） | `.claude/rules/<领域>/<name>.md`，带 `paths:`，不超过 10 行 | 读/改到匹配文件时 |
| 有步骤的流程 | `.claude/skills/<name>/SKILL.md` | 启动时只有 description |
| 以上几处的扩展内容（历史决策、试过的方案、实测数据、坑的详细经过、外部系统调研） | `.context/<领域>/<slug>.md`，原处留指针 | 读到指针、且任务符合"什么时候读"时 |
| 挂不到代码上的背景（评估过但没做的需求、外部系统限制、还没有代码的决定） | `.context/<领域>/<slug>.md`，登记在 `.context/README.md` | 根 CLAUDE.md 常驻一行指向入口，做新需求前查 |
| 个人偏好 / 环境绑定 | 不进仓库，留在自动记忆 | — |

monorepo 中，只涉及一个包的内容放进该包自己的 `CLAUDE.md`、`.claude/`、`.context/`，跨包内容放在仓库根。

### 为什么单个文件不用 rule

`paths` 只匹配一个文件的 rule，碰到这个文件就整条加载，Claude 只读文件的一部分时也一样，所以它在 token 上和写在文件里的注释没区别，反而离代码更远、定位不到函数。rule 的优势在于一条覆盖很多文件，所以只留给几个文件共用的内容。

### 为什么用指针，又怎么不漏读

全量写在原处的内容一定被看到，但大多数任务用不上；拆进文档能省 context，代价是 Claude 可能该读的时候没去读。context-keeper 用三点把漏读的风险压下来：

1. **必须知道的那一句留在原处。** 指针写成「重点 + 什么时候读 + 路径」，坑和约束的结论就在重点里，没去读文档也不会踩坑，漏掉的只是细节。
2. **"什么时候读"写成动作**（"改重试次数前读"），不写成话题（"原因见"），Claude 拿它和当前任务一对照就知道要不要读。
3. **pointer-guard hook 兜底**：Claude 要改的代码附近有注释指针、而本会话还没读过那份文档时，拦下这次编辑一次，让它按触发条件决定先读还是直接重试。

```ts
// 重试上限 3：网关连续 5 次失败会封 IP 10 分钟。改重试次数或退避前读 apps/web/.context/api/retry-policy.md（事故经过、试过的熔断方案）
const MAX_RETRY = 3;
```

两三行就说完的不拆，直接写在原处。

## 怎么起作用

**写入端**

- `record-context`：要记一条项目知识时，决定它写到哪里，按模板写入，并登记进对应入口。
- 根 CLAUDE.md 的「更多上下文」索引里有一行常驻的写入约定，让 Claude 默认不把背景写成长注释或只记在自动记忆里。
- comment hook（PostToolUse）：Claude 写入 4 行以上的独立注释块时，提醒它注释只留一句重点，扩展内容进 `.context/`、原处留指针。只提醒、不阻断，JSDoc、license、行尾注释不算。设环境变量 `CONTEXT_KEEPER_COMMENT_HOOK=0` 可关闭。

**读取端**

- 代码注释：读到那段代码时就在眼前，扩展内容的指针也在这里。
- rule：碰到匹配的文件时自动加载。
- pointer-guard hook（PreToolUse）：改到带 `.context/` 指针的代码、而本会话还没读过那份文档时拦一次。"附近"指改动范围内、外层函数 / 类的声明和紧贴其上的注释，以及文件头注释（文件开头、后面是空行或 import 的那几段，开头的 `<?php`、`'use client'`、`<script>` 标签跳过）；同一会话每处指针只拦一次（和拦下它的那次编辑在同一条消息里的后几个 Edit 继续拦，免得漏过去），文档读过（Read 成功，或 Bash 里用 cat / head / tail 这类命令读过；读失败、`git add` 这类只是提到路径的不算）之后指向它的指针都不再拦，主会话压缩上下文后拦过、读过都重新算；主会话和每个子代理各算各的。行注释、块注释（含 JSX 的 `{/* */}`）和 Python docstring 里的指针都认。拦截消息里带文档的绝对路径，会话开在子目录里也不会拼错。不是 git 仓库的项目，拿启动会话的目录当项目根。拦下时也会提醒：改完后指针里的重点或文档不再成立的，一并更新。设环境变量 `CONTEXT_KEEPER_POINTER_HOOK=0` 可关闭。
- 领域索引 rule `.claude/rules/<领域>/context-index.md`：`paths` 覆盖这个领域的代码，正文是领域里多处都该知道、又不属于某一处的长文档，每份一行「重点 + 什么时候读 + 路径」：重点随 rule 进 context，细节按需读。
- 文档入口 `.context/README.md`：挂不到代码上的文档，同样每份一行「重点 + 什么时候读 + 路径」，根 CLAUDE.md 里常驻一行：

  ```markdown
  - 做新需求、评估方案前，先看 `.context/README.md`：评估过但没做的需求、外部系统限制、还没有代码的决定
  ```

**整理与体检**

- `organize-context`：把现有项目迁移到这套结构，已经在用的项目则做体检。始终在 plan mode 里出计划（不在会先进入），批准后才动文件。也能把自动记忆里与环境无关的内容沉淀进项目。
- `scripts/check.mjs`：确定性检查，skill 会自动调用，也可以手动跑：

  ```bash
  node <插件目录>/scripts/check.mjs [路径] [--comments]
  ```

  检查 rule 的 `paths` 是否生效、rule 是否过长、单文件 rule、没写"什么时候读"的指针、没有重点的登记行、`@` import、`.claude/rules/`、`.claude/skills/`、`.context/` 有没有被 `.gitignore` 忽略、文档命名、失效指针、孤儿文档、文档入口有没有被根 CLAUDE.md 指到等，失效指针只查 CLAUDE.md、rule、skill、`.context/` 文档和源码里的注释，其他 Markdown、代码块里的示例路径和源码字符串里的路径不算。有错误时退出码为 1。没有依赖，接 CI 时把 `check.mjs` 连同 `lib/` 目录一起复制进项目。

## 改造前后

改造前，`apps/web/src/api/retry.ts`：

```ts
// 重试次数固定为 3。以前是 5 次，但上游网关连续 5 次失败
// 会把客户端 IP 拉黑 10 分钟，线上出过一次事故。
// 首次 + 3 次重试 = 4 次，留一次余量。
// 试过在网关前加熔断，和网关限流叠加后导致长时间不可用，放弃了。
// 退避从 200ms 起指数增长。
const MAX_RETRY = 3;
```

改造后，注释只留重点和指针，事故经过、试过的熔断方案进 `apps/web/.context/api/retry-policy.md`：

```ts
// 重试上限 3：网关连续 5 次失败会封 IP 10 分钟。改重试次数或退避前读 apps/web/.context/api/retry-policy.md（事故经过、试过的熔断方案）
const MAX_RETRY = 3;
```

只改这个文件里别的函数时，这些历史不会进 context；要改重试逻辑时，指针和 pointer-guard 会把 Claude 带到文档。

## 从 0.4.x 升级

0.5.0 调整了注释、rule 和文档的分界：

- 只涉及一个文件的内容写成代码注释，不再写成单文件 rule；rule 只留给几个文件共用的内容和没法写注释的文件
- 注释、rule、CLAUDE.md 里只留必须知道的那一句，扩展内容进 `.context/`，原处留「重点 + 什么时候读 + 路径」的指针；rule 正文上限从 20 行降到 10 行
- 新增 pointer-guard hook：改到带指针的代码、本会话又没读过那份文档时拦一次
- 检查脚本新增：单文件 rule、没写"什么时候读"的指针；被代码注释指到的文档不再要求登记进领域索引

升级后跑一次 `organize-context`，它会列出要改写成注释的单文件 rule、要拆出扩展内容的长 rule，以及要改写的指针，批准后执行。

0.5.1 修了几处评审发现的问题：

- pointer-guard 改成每处指针拦一次（原来是每份文档一次，同一份文档的第二处指针不会拦）；紧贴第一个声明的首段注释不再当成文件头；折行的指针会把整段注释给出来
- 检查脚本："没写什么时候读"不再把路径后面紧跟的中文一起删掉（误报），也不再把"以前""超时"当成触发条件（漏报）；被 CLAUDE.md 某一行指到的文档不再报缺领域索引
- `organize-context`：CLAUDE.md 条目、单文件 rule 改写成注释要块 A、B 都批准才执行
- 改动让指针里的重点或文档过时时，同一次改动里更新（拦截消息、写入约定和 `record-context` 都加了这一条）。已有项目的根 CLAUDE.md 写入约定那一行，下次跑 `organize-context` 时按新模板补

0.5.2 修了几处评审发现的问题：

- pointer-guard：主会话和子代理各算各的（原来主会话读过或被拦过，子代理就不拦了）；拦下后 3 秒内对同一处的编辑继续拦（原来同一条消息里的第二个 Edit 会直接放行）；不再按扩展名表筛文件，`.proto`、`.graphql` 这类文件里的注释指针也拦
- 检查脚本：扩展名表补了 `.proto`、`.graphql`、`.prisma`、`.jsonc`、`.ini` 等能写注释的格式，表里没有的非 Markdown 文件里指到文档的路径也算已登记（原来报孤儿文档）；路径参数相对当前目录找不到时按仓库根解析；`--comments` 不再把已经带指针的短注释列成搬运候选；"前最好读""前一定要读""时也要读"这类写法不再报没写什么时候读
- 长注释块的阈值从 5 行降到 4 行，和"注释 1–3 行"对齐，comment hook 和 `--comments` 都按 4 行算
- `record-context`：被 comment hook 提醒而来、但背景不值得记的，直接把注释删掉或缩短；拆注释不占"最多三条"

0.5.3 修了几处评审发现的问题：

- pointer-guard 的"读过"收紧：Read 要成功才算（原来路径拼错、读失败也算），Bash 只认 cat / head / tail 这类读文件的命令（原来 `git add`、`ls` 提到路径也算）；拦截消息里给出文档的绝对路径
- pointer-guard：主会话压缩上下文后，拦过的指针也重新拦（原来只有"读过"重新算，拦过的不会再拦）；JSX 的 `{/* */}`、不带 `*` 前缀的多行块注释、Python docstring 里的指针也认（原来检查脚本算它们已登记，hook 却不拦）
- 检查脚本："什么时候读"改成按排除来认，"前阅读""时对照""前确认"这类写法不再报没写；只排除"以前""超时""前端""时间"这类词
- 判据："涉及几个文件"按谁需要知道算。约束调用方的（"必须在 X 之后调用"）写进定义处的 API 文档注释，或写成 `paths` 覆盖调用方的 rule，不写成定义上方的普通注释
- `organize-context`：迁移模式的作用域也处理脚本报出的问题和已有的文档；只有 rule、还没有 `.context/` 的作用域明确算体检；执行时被 pointer-guard 拦下是预期的，直接重试
- 加了测试，改脚本后跑 `node --test "plugins/context-keeper/tests/*.test.mjs"`

0.5.4 修了几处评审发现的问题：

- pointer-guard：文件头注释前面的 `<?php`、`'use client'` 这类指令、Vue / Svelte 的 `<script>` 标签不再算代码（原来 PHP 文件、指令写在注释前面的文件里，文件头的指针不拦）
- pointer-guard："拦下后继续拦"改成按消息算：和拦下它的那次编辑在同一条消息里的继续拦，Claude 看到拦截消息后重新提交的放行。原来按 3 秒算，重试得快会被多拦一次，同一条消息里隔了一个慢命令的第二个 Edit 又会漏过去；查不到消息 id 时仍按 3 秒算
- pointer-guard：不是 git 仓库的项目，拿启动会话的目录当项目根（原来整个不生效）
- 检查脚本：源码里只查注释里的指针，字符串里的路径（输出文件名、测试数据）不再报失效、不再报没写什么时候读，指得到文档的照样算已登记
- 检查脚本：只匹配一个生成物或 lockfile 的 rule 不再报单文件 rule（`generated/` 目录、`.generated.` / `.pb.` 这类文件名、`pnpm-lock.yaml`，或文件头几行写着 generated / do not edit）；`record-context` 写明这类 rule 保留

0.6.0：`organize-context` 始终在 plan mode 里运行。不在 plan mode 时先调用 EnterPlanMode 进入，计划用 ExitPlanMode 提交；进不去（工具不可用或用户拒绝）就停下来让用户切到 plan mode 后重跑，不再把计划写进回复里等同意。

0.7.0：领域索引 rule 和 `.context/README.md` 的登记行必须带重点。

- 原来的登记行是「路径 + 什么时候读」，入口进了 context，Claude 什么都没得到，要读完整份文档才拿得到重点，重点和细节还是一起加载。现在和普通指针一样写成「重点 + 什么时候读 + 路径」：文档里不知道就会做错的结论（坑、约束、已知限制）写在这一行，文档里没有这类结论的（纯参考）才省掉
- 一份文档的重点一句话写不完的，不进索引，单独写成一条 rule（这几条结论加指针）
- 检查脚本新增提示：文档入口、领域索引 rule 里以路径开头的登记行，以及正文只有这种行的 rule

升级后跑一次 `organize-context`，它会列出要补重点的登记行，批准后执行。
